## [Unreleased]

### Added
- **The Classifier's Vendor Vocabulary Is Derived From the Shipped Tiers Instead of Written By Hand (`@blockingmachine/core`, `@blockingmachine/browser-extension`, `scripts`)**:
  - The extension carries two bodies of knowledge about what is worth blocking, and the *gap* between them was the only thing that was ever measured. The tier/model agreement suite pinned every host a tier shipped that the model could not place — 46 of them — and the way out of that pin was a person: read the entry, work out which vendor the host was, and type the token into `reputation.ts`. That loop does not scale, and what it produces is unauditable. The pin is now the **input**. New `packages/core/src/ai/tierVocabularyDerivation.ts` turns the disagreement set into the vocabulary, `scripts/derive-tier-vocabulary.mjs` drives it from the tier files, and the result ships as the generated `packages/core/src/ai/tierVocabulary.generated.ts`, wired in through `npm run derive:vocabulary` and `npm run check:vocabulary`.
  - **The seed corpus is the disagreement set, and the derivation cannot invent coverage.** Every host a tier ships that the model cannot place becomes a seed, tier by tier, and every token comes from the name of a host that is *already shipped* — so this can name what the tiers contain and cannot reach past them. **44 seeds produced 42 tokens: 12 ad and 30 tracker.** The measured effect on the real tier files: `Ad networks` **24 of 36 hosts recognised → 36 of 36**, `Tracking & analytics` **23 of 36 → 35 of 36**, `Consent & nags` **1 of 22 → 21 of 22**, and the pin **46 → 2**.
  - **Three things decide admission, and only the first is about the tiers.** (1) *The model has to move*: the candidate token is installed into the live lists and the host is classified again — asked of the model itself through a new `withTemporaryVocabulary`, so a token that looks like a name but is not the signal is refused instead of assumed to work. (2) *The tier has to accept the family*: `TIER_MODEL_FAMILIES` is the same contract the agreement suite grades with, enforced during the derivation rather than asserted afterwards, so a token that files a `tier_ads` host under telemetry has not placed it in the tier's sense. (3) *The independent labelled corpus has to hold*, and it is evaluated **per candidate rather than per run**, so one wrong token costs itself instead of the whole vocabulary: a new false positive on any clean domain **by name** (so a candidate that trades one broken domain for another is refused, not counted as break-even), a clean domain called malware, or a regression in accuracy, macro F1 or list-coverage gaps. A vocabulary derived from the tiers and then graded against the tiers would prove nothing, which is why the third gate exists, why `--write` refuses to write when it fails, and why `tier_security` is deliberately **not** a source: its contents are the model's own verdicts, so learning from it would teach the classifier the answers it is graded on.
  - **What the tokens may be is stated rather than implied, and the refusals are the interesting half.** Five characters minimum, because an abbreviation that short belongs to somebody else (`ad`, `ct`, `tr`) and the short tokens that are deliberately kept are hand-written where a person can defend them. Function words and ordinary English refused — `privy` is a real consent vendor *and* a real word, so the tiers keep shipping a host the vocabulary refuses to name, which is the safe direction to be wrong in. Compound labels are judged as written and never split, so `privacy-mgmt` cannot become a `privacy` token that matches a hundred legitimate hosts. Two consumer platforms are tokenised at the tracked *endpoint* rather than the brand, and the derivation proves why rather than assuming it: it tries the brand form, and the labelled corpus refuses `tiktok` because installing it calls `tiktok.com` an ad host. The 22 vendored entries that were hand-written are gone from both lists — 12 ad and 10 tracker names, every one re-derived from the tier host that justified it — so the hand-written lists now hold only what a machine cannot honestly derive: `fpjs` (four characters), and `ct.pinterest` and `business-api.tiktok` (endpoints on consumer platforms whose brand form is a false positive).
  - **The provenance travels with the tokens.** `TIER_VOCABULARY_PROVENANCE` records the hand-written seed counts, how many hosts each tier contributed and how many it could not place, the corpus before and after, and the gate's own sentence, and `TIER_VOCABULARY_EVIDENCE` records which host justified which token and the family it places it in. A generated list without its measurement is a hand-written list with extra steps: the next reader cannot tell whether the gate passed or was never run.
  - **The bug that made the whole thing checkable, found by running it.** The first version seeded its seed pass with the *shipped* vocabulary, so `--write` was immediately followed by `--check` failing on the file it had just produced: after the write the model already placed the hosts it had derived tokens for, the disagreement set shrank, and the next render differed. The derivation now starts from the hand-written lists alone, installed by **replacement** (`withTemporaryVocabulary({ replace: true })`, which moves `mergedListsCache` and the exported arrays together — `isBenignServiceEndpoint` reads the exported list directly and the classifier reads the live db, so installing one without the other would answer "would this token change the verdict?" with a verdict the shipped build could never produce). That makes the derivation a **fixed point**: run it twice and the bytes are identical, verified against the real tier files and after a core rebuild, which is the version that also puts the derived tokens live in the shipped lists.
  - **The seed pass, the corpus gate and the provenance block are stated in core rather than in the script**, because two callers need the *same* ones — the run that writes the file and the suite that re-derives it — and a pin that is graded twice by two implementations is a pin that drifts. `tierVocabularySeeds` walks the tiers, `compareTierVocabularyCorpus` is the gate as a pure function of two measurements, and `tierVocabularyProvenance` assembles the record, so the driver and the suite cannot disagree about what "the corpus passed" or "unplaceable" means.
  - **Measured end to end.** 118 curated hosts → the verdicts of 209 corpus cases before and after: exact category accuracy **98.1% → 99.0%**, macro F1 **0.867 → 0.876**, list-coverage gaps **4 → 2**, with **zero false positives across all 122 clean domains** and none of them called malware. The derivation also lifted the evaluation corpus's own consumer-platform coverage, so `tiktok.com`, `pinterest.com`, `snapchat.com` and `facebook.com` joined the corpus's clean cases — a vocabulary that flags a consumer site has to fail a case that says so.
  - **The tier/model pin is now machine-written.** `tierModelAgreement.test.ts` reads its tolerated misses out of `TIER_VOCABULARY_REJECTIONS` instead of typing them, and the two are the same set for a structural reason the suite's comment states: the shipped vocabulary is the hand-written one plus the derived tokens, so the suite disagrees about no more hosts than the derivation seeded on, and the derivation only refuses a host no derived token placed. Two gaps remain and the record says which is which — `business-api.tiktok.com` (the one candidate that moved it was refused by the corpus, and the endpoint token it does carry is outranked by the infrastructure pass calling an `-api` zone on a major platform a verified endpoint, which is correct precedence) and `privy.com` (no label of the name survives the vocabulary rules). The suite also stopped restating the tier families: it imports `TIER_MODEL_FAMILIES` from the module that derives the vocabulary, so there is one definition of what agreement means rather than two that happen to match.
  - 51 new tests (core 1125, up from 1082; extension 423, up from 415). Core unit-tests the rules rather than the output — length and function-word refusals, compound labels kept whole, the two candidate forms and their order, the seed pass's per-tier coverage, every way the corpus gate refuses and the one way it does not, the derivation's per-candidate refusal and its idempotence, and the merge contract in `reputation.ts` including that `withTemporaryVocabulary({ replace: true })` installs exactly what it was given and restores it even when the callback throws. The extension suite re-derives the file **from the tier files as they are on disk**, in process, through the same core functions the driver calls, and compares it byte for byte with what is checked in; it also re-checks every evidence entry by installing the token and asking the model, refuses to accept a rejection for a host the model can place, and asserts that placed-plus-refused covers the whole disagreement set with nothing left unexplained.
- **A Fifth Tier Holds the Classifier's Malware Verdicts, Shipped Separately From the Ad and Tracker Tiers (`@blockingmachine/core`, `@blockingmachine/browser-extension`, `@blockingmachine/electron-app`, `scripts`)**:
  - The project has two bodies of threat knowledge and shipped one of them. The curated `security` module and the OISD security list feed the blocklist; the embedded classifier walks the same hosts and returns a verdict the tiers had no home for, so **6,392 `Malware/Phishing` verdicts over the hub's real 190,035-host list were computed, reported in the radar, and then discarded** — they could only ever block by accident, through a name that happened to read as malware. New `tier_security`, *Threat & malware*, is that home, and it ships **separately from the ad and tracker tiers** so enabling one is not a decision about the other.
  - **The tier contains the classifier's verdicts and nothing else, which is why the curated threat lists still do not map into it.** `CATEGORY_TIERS` keeps `security` mapped to no tier — routing those lists by category is exactly what the previous entry refused, and the measurement behind that refusal is now explicit: over the project's own 34-host `blockingmachine-security.txt` the classifier calls **28 hosts `Clean`, 6 `Advertising`, and 0 `Malware/Phishing`**. A tier whose membership rule is "the model said malware" cannot be filled from a list the model disagrees with, or the tier/model agreement suite would be grading a contradiction it created. `CORE_INDICATORS` is likewise unchanged and still routes on the *name*: a host called `malware.example.com` reaches `tier_core`, which ships enabled, so a fresh install still blocks name-evident threats. The two tiers specialise by the kind of evidence behind them — a name a publisher chose, and a verdict a model reached — rather than by how bad the host is.
  - **It ships off, and the catalogue says why in the type system rather than in a comment.** `defaultEnabled: false` in the catalogue and in the manifest's `rule_resources`, because this is the one tier whose contents cannot be audited by reading a filter list: a host is here because a model said so, and unlike every other tier there is no publisher claiming it. The catalogue also gains `curatedSeed`, and `tier_security` sets it `false` — the flag is what lets the three places that assert "a tier is non-empty" tell a lost baseline from a tier that legitimately has none. `rules/tier_security.json` is `[]` in a fresh checkout, which is the correct state rather than a defect: the validator allows it for a compiled-only tier, the compiler's `--check` skips its count comparison, and the agreement suite skips its non-empty assertion. Empty is also structurally required to be legal here, since the tier is rebuilt from scratch every run.
  - **The hub writes the verdicts beside the lists they are verdicts about.** `packages/electron-app/src/index.ts` classifies every distinct host in the compilation it is already building — the same run that writes the per-category attribution — and writes `filters/output/malware.txt` with a provenance header naming itself as a model verdict rather than a publisher list. The compiler discovers that file (`--security <file>` to name one, `--no-security` to ship the tier empty), and because discovery is the default it is reported on every run: either the source and the count, or `no classifier verdict file found — tier_security ships empty`. The tier's share of the 30,000-rule budget is **12% — about 3,600 slots**, sized by measuring what the classifier actually produces rather than by taste: classifying the real 190,035-host list takes **161,846 ms (0.852 ms per host)** and yields those 6,392 verdicts, so the share is neither tighter than what the model finds nor larger than what it could fill. A share is a cap and never a reservation, so an absent verdict file wastes nothing — the unspent capacity is redistributed as it always is.
  - **Verdicts accumulate nowhere, so the classifier can withdraw a false positive.** The curated tiers are compiled *additively* on top of the files on disk, which is right for hand-picked hosts and wrong for a model's output: a host the model flags once and then clears would stay blocked forever. `readCuratedTiers` skips `COMPILED_ONLY_TIERS`, so `tier_security` has no seed to preserve and is rebuilt from the current verdicts on every compilation. Verified by running the real compiler: **2 verdicts ship 2 rules; withdraw one and the next run ships 1; run it against an empty verdict file and the tier ships 0 rules and the file on disk becomes `[]`.** A blocklist that cannot shrink is a blocklist that keeps someone's first mistake, and this one shrinks.
  - **Wiring the tier exposed a planner regression that would have disabled the evidence basis for good, and fixing it is the part that mattered.** `planTierBenefits` refuses to weight a plan by measurement while *any* tier is unmeasured — deliberately, because a disabled tier's zero is not a measurement — and a tier that ships empty and off can never be measured, so **every plan on every fresh install would have fallen back to rule counts permanently**. New verdict `empty`: a tier carrying no rules has nothing to block with, so no amount of traffic will ever answer for it, and it is taken out of the question instead of counted as an unanswered one. It is never called idle ("turn this off" is not advice for a tier that cannot act), and `formatTierBlocking` leaves it out of "2 of 4 tiers" because counting it would present an unwinnable tier as a failure. `planTierSelection` needs the same exemption on its own side of the gate, since the popup hands over a benefit only for the tiers the ledger judged and an empty tier therefore arrives with no number at all. The gate still bites where it should: a **disabled tier that carries rules and has no history still forces coverage and is still named**, which is pinned as the negative control. Measured end-to-end against the real shipped tier files and a real ledger: with `tier_security` empty and three neighbours off, 4,800 attributed blocks give `evidence` across four tiers; drop the ad tier's history instead and the same call returns `coverage` and names `tier_ads`.
  - **Five tiers where there were four moved the arithmetic in five suites, and one of those moves is a real consequence.** Catalogue-shape fixtures now enumerate five (`status.tiers`, the tier/model agreement families, the CLI's and core's row arrays, the compiler's `--budget` cases). The interesting one: at `--budget 8` a fifth share in the pool rounds the annoyances cap to nothing, its curated host is left unserved, and the compiler now **refuses the run** rather than dropping it — the guardian behaving exactly as designed at a budget that is pathological precisely because the pool is now split five ways — so the determinism case compiles at `--budget 20`, where every curated seed fits and the redistribution it is actually about still runs. The popup also gained the `.tier-row.tone-security` rail it was missing: the element-AI tone map had four entries for five categories, and the threat tier now takes the danger colour, since an element is an ad, a tracker, a nag or content and a host the model calls malicious is none of the four.
  - 6 new tests (extension 415, up from 409, plus one renamed; core 1082, up from 1081; the CLI and the hub unchanged): an empty tier graded `empty` rather than silent, an empty tier not counted among the tiers that blocked nothing, the tier/model agreement suite's **inverted** invariant — `tier_security` is the only tier whose allowed family is `Malware/Phishing`, so a host in it the model calls `Clean` is the defect and the assertion is flipped rather than dropped — and the planner-side pin that an empty tier neither blocks the evidence basis nor changes what it selects. Three expectations moved for reasons worth reading: the CLI's "empty files break every tier" assertion is now `curatedSeed`-scoped, because an empty `tier_security` is not a broken one, and its fixture writes the tier as an empty file rather than omitting it, which models the honest state instead of a corrupt bundle the command is right to refuse.
- **The Classifier Learns the Vendors the Shipped Tiers Carry, and the Tier/Model Pin Shrinks by 24 (`@blockingmachine/core`, `@blockingmachine/browser-extension`)**:
  - **Superseded in part, and worth reading as the step before it:** the tokens this entry adds by hand are now *derived* from the tier hosts that justify them — see the derivation entry above — and the hand-written lists no longer carry them. The pin this entry reports as **46 → 22** is now **46 → 2**, and it is no longer typed into the test at all.
  - The tier/model agreement suite pinned **46 curated hosts** the Mini-AI classifier would not place — it called every one of them `Clean` at 74–88%, below the mark past which a clean verdict is an assertion rather than a shrug. The pin was doing its job (it exists so the extension cannot block a host while the classifier it also ships calls that host clean), but half of it was not a limitation of the model: it was **missing vocabulary**. A vendor whose name is its product name — Magnite, MoPub, Sonobi, Comscore, Nielsen, AddThis — reads as an ordinary word to every lexical feature the classifier has, so twelve SSPs and exchanges and twelve measurement vendors sat in the pin for no better reason than that nobody had written their names down.
  - **The fix is the vocabulary, not the assertion.** 12 tokens joined `SUSPICIOUS_AD_TOKENS` and 11 joined `SUSPICIOUS_TRACKER_TOKENS`, following the list's existing idiom (`` criteo ``, `pubmatic`, `scorecardresearch`, `datadoghq` are all brands there already). The result on the real tier files: **`Ad networks` 24 of 36 hosts recognised → 36 of 36, `Tracking & analytics` 23 of 36 → 35 of 36**, with `Core shield` still 24 of 24 and `Consent & nags` untouched at 1 of 22. The pin drops **46 → 22**, and every one of the 24 that left did so because the classifier learned the vendor — none because the pin was relaxed. `tier_ads` now has *no* tolerated misses and its key is deleted rather than left as an empty array, so a host added to that tier falls through the `?? []` default and fails instead of being silently tolerated.
  - **Two consumer platforms are tokenised at the endpoint, not the brand.** A bare `pinterest` or `tiktok` token would have called the consumer sites themselves trackers — true of neither, and exactly the false positive this list exists to avoid. The tokens are `ct.pinterest` and `business-api.tiktok`, the hosts the tier actually ships, so the vocabulary grows without the false-positive budget moving. A 58-domain sweep of ordinary sites plus purpose-built near-misses of every new token (`nielsenmedia.com`, `mopubcdn.com`, `sonobistats.com`, `tremorstudios.com`, `cash.app` …) confirms it: the only hits are `business.tiktok.com`, which was already flagged before this change because it is registered in the tracker-network list, and `dynamicyieldlabs.com`, a synthetic domain that trips the same ≥11-character substring rule `scorecardresearch` and `datadoghq` have always used.
  - **The evaluation corpus measures the improvement rather than being told about it.** Over the 205-domain labelled corpus: exact category accuracy **97.6% → 99.0%**, macro F1 **0.863 → 0.876**, list-coverage gaps **5 → 2**, lexical recall unchanged at **100% of 81 name-evident threats**, and **false positives unchanged at 0**. Calibration moves in both directions and the report says so — Brier improves (**0.0252 → 0.0163**) while ECE rises to **0.031**, still far inside its 0.15 budget, because a newly-placed host is reported at the capped 70% single-signal confidence rather than being absent. The coverage-gap ceiling was a `<= 5` ratchet sitting exactly at its limit; it is now an assertion on the exact remaining pair, so a change that quietly adds a third gap fails instead of fitting under a loosened headroom.
  - **What the remaining 22 are, and why they are pinned for two different reasons.** 21 are `Consent & nags` hosts the *domain* classifier has no category for — there is no annoyance or consent family to place Onetrust, Cookiebot or Osano in, which is the measurable reason that tier ships disabled, and no amount of vocabulary fixes a missing category. The 22nd is `business-api.tiktok.com`, and it is the informative one: it now *has* a token and the token does raise the model's telemetry probability on it (0.04 → 0.12), but the verdict does not move because the `-api` label makes the infrastructure pass classify the host as a verified endpoint on a readable domain, and `knownSafeInfra` outranks every token in the model by design. That precedence is correct — an API zone on a major platform is precisely the shape a naive token match gets wrong — so the host stays pinned with the reason written next to it, rather than the token being tuned until the number turns green.
- **A Tier That Duplicates the Synced List Is Now Detectable, Because Counting Hits Could Never Say So (`@blockingmachine/core`, `@blockingmachine/cli`, `@blockingmachine/electron-app`)**:
  - Every tier in this project is ranked by what it *blocked*, and there is a question that number is structurally incapable of answering: **does this tier block anything the dynamic rules do not?** A ledger is a record of past traffic the browser happened to see, so a tier whose every host is already in the synced list looks exactly like a tier doing work — the rules that fire look entirely ordinary, and they fire for a tier that is spending the browser's guaranteed static slots on coverage the dynamic quota was already carrying. No amount of counting hits distinguishes the two.
  - **Redundancy is a set difference over hosts, computed with no ledger at all.** New `readSyncedHosts` and `findTierRedundancy` in `packages/core/src/tierPlanInput.ts` reduce the synced list to the hosts it blocks and each tier to the hosts its rules block, and report per tier how many rules the list already covers plus whether the tier adds **nothing** at all. Because it needs no browser and no history, a user who has never browsed gets the same answer as one who has, and the answer is a property of the two files rather than of anyone's afternoon.
  - **The diff is one-directional, and both wrong directions are tested.** A dynamic rule for `doubleclick.net` covers `ads.doubleclick.net`, so a tier shipping the subdomain adds nothing — a suffix walk up the labels, not a lookup. The reverse does **not** hold: a synced rule for `ads.doubleclick.net` leaves the apex and every other subdomain open, so the tier shipping `doubleclick.net` is still doing work, and treating that as coverage would let one narrow synced rule retire the broadest tier in the bundle. Matching is by label sequence rather than `String.endsWith`, so `notdoubleclick.net` is not counted as covered by `doubleclick.net`.
  - **An exception is where a tier is *not* redundant, so the reader keeps exceptions in their own set.** `@@host^` and the `!@@host` hosts-file spelling are on the record because they *allowed* a request; a list that excepts a host does not block it, and a tier shipping it is the only thing left blocking it. Dropping the exception would report the tier as redundant precisely where it is load-bearing — the same inversion the ledger reader refuses when it declines to credit `@@` lines.
  - **A rule scoped to a request type cannot stand in for the unscoped rule it resembles, and getting this wrong was the first real finding.** The obvious implementation strips `$` modifiers and compares hosts, which credits `||scoped.com^$script` as full coverage of `scoped.com` — but that rule blocks scripts and leaves the host's images and frames alone, so a tier shipping `||scoped.com^` blocks strictly more and is *not* duplicated by it. `$third-party`, `$popup`, `$domain`, `$script` and `$image` all narrow, and on the real synced list those are not an edge case: **127,591 of 316,699 blockable lines name no whole domain.** `$important` and `$all` are the other side of that line — priority and a synonym for every resource type — so they do count. Refusing the scoped rule under-reports a tier covered only by a pile of per-resource-type synced rules, which is rare and costs nothing; crediting them over-reports on partial evidence.
  - **Both halves of the read are printed, because the difference is the honesty of the report.** `blockingmachine tier-plan --synced <browser.txt>` now prints the redundancy block beneath the plan: which tiers add nothing, how many rules of every other tier the list already covers, and — as its own line — `316,699 blockable lines read, 127,591 naming no whole domain (cosmetic filters and rules scoped to a request type, which a domain rule exceeds)`. Quoting only the host count would hide that most of a real synced list is unusable to a domain-level comparison, and a reader who assumed otherwise would read a small redundancy figure as a complete one. Absent the flag the block says redundancy is *unknown* rather than printing a table of zeroes, which is a claim about a comparison nobody ran.
  - **The hub finds its own synced list, because the hub is what writes it.** New `findSyncedListPath()` looks beside the compiled output for the `browser.txt` the extension actually fetches — the same bytes, so a redundancy report can never be about a list the browser was never given — and a checkout that has never compiled reports redundancy as unknown rather than as an empty list that would mark every tier entirely redundant. The card gains an **Already dynamic** column (an em dash, not a zero, when nothing was compared), names the tiers that add nothing, and states the caveat in the same breath: a redundant tier is duplicated coverage rather than absent coverage, it still costs static slots, and it buys that coverage back the day the synced list drops a host.
  - **Measured against the real synced list and the real shipped tiers.** The hub's own `browser.txt` — 13.0 MB, 358,818 lines — reduces to **186,533 blocked hosts and 1,725 exceptions in 184 ms**, with 316,699 blockable lines read and 127,591 refused. Against the four shipped tiers it reports **Core shield 23 of 24 rules already blocked dynamically (95.8%), Ad networks 34 of 36 (94.4%), Tracking & analytics 27 of 36 (75.0%), Consent & nags 7 of 22 (31.8%)** — and **no tier entirely redundant**, which is the outcome that makes `complete` worth carrying separately from the ratio: three of these four are mostly duplicated, and mostly duplicated is a different decision from adding nothing.
  - 18 new tests (core 1081, up from 1071; CLI 64, up from 60; electron 318, up from 314): blocks and exceptions in both spellings, comments and cosmetic filters and scoped rules all refused, a parent-host synced rule covering a tier's subdomain, the reverse direction refused, a suffix-sharing neighbour not covered, an exception restoring a tier host, `complete` only on a fully duplicated tier, an empty tier not counting as redundant, an absent synced list reporting unknown rather than zero, and the CLI and the card rendering the same findings from the same computation. Two of the new expectations were wrong first: the default fixture had `tier_ads` shipping exactly the two hosts the list covered, which made it fully redundant and not the half-covered tier the test described. Tightening the no-ledger card assertion found a **pre-existing hole** as well — it was passing on an em dash inside a fixture's explanation string rather than on any table cell, so it now nulls the fixture's hit counts and scopes the check to one row.
- **The Hub's Tier Plan Can Actually Be Weighted by a Ledger, Which It Never Could (`@blockingmachine/electron-app`)**:
  - The plan is weighted by measured blocks in the extension popup and in `blockingmachine tier-plan`, but the hub's card called `get-extension-tierPlan` with no arguments, so it reached `computeTierPlan` with no ledger and **planned by rule count every single time** — while displaying a card whose entire reason for existing is to weigh tiers by what they block. The surface a user checks before shipping a build was the one surface that could never do it.
  - The cause is structural, not a missing argument: **the hub holds no measurement of its own.** The extension accumulates the blocks in its own storage and the user exports them from the popup, so the only per-tier counts that exist anywhere are in a file the user chose to keep. The card now says so and offers to be pointed at that file, and the main process remembers the choice in a new `tierLedgerPath` store key — deliberately, because a plan weighted by measurement and a plan weighted by rule count can disagree completely, and a hub that reverted to rule counts on each launch would be answering a different question every time it was opened. Choosing or forgetting a ledger re-plans immediately, so the change of basis is visible while looking at the card rather than at the next restart.
  - **A chosen ledger that has since moved is reported as missing, not ignored.** "The ledger you picked is gone" and "you have no ledger" lead to different decisions about which one to go and get, so the card names the path and the reason, and offers to choose it again — while still rendering the plan it fell back to, ranked by rule count and labelled as such, rather than replacing a working answer with an error.
  - 3 new tests (314 in the package, up from 311): the offer to choose a ledger, the chosen path with a way to forget it, and the missing-ledger case asserting the fallback is *labelled* rather than silent.
  - **What it will actually show today, measured through the same function the hub runs:** against the shipped tiers and the one real ledger in the repository — Core shield 24 rules / 12 measured, Ad networks 36 / 1, Tracking 36 / 7, Consent & nags 22 / 0 — the hub's manifest default (only `tier_core` on) leaves three tiers switched off with no history, and every tier on together still leaves Consent & nags *unobserved*, because 20 measured blocks is under the 50-match sample. So the hub is now **capable** of weighting by measurement and today correctly declines to, naming the tier it could not judge. That is the gate working, and it is the same answer the popup gives.
- **The Tier Plan Is Now Answerable Outside a Browser, and All Three Surfaces Run One Function (`@blockingmachine/core`, `@blockingmachine/cli`, `@blockingmachine/electron-app`, `@blockingmachine/browser-extension`)**:
  - The capacity plan decides what a packaged extension ships, and it was only reachable inside a browser — against a live static-rule grant that accounts for how congested the shared pool is. That number decides the outcome (a plan is trivial at the guaranteed 30,000 and contested well below it), and it does not exist outside a browser, so the question was unanswerable at exactly the two moments that matter: deciding what to ship from the hub, and reviewing on the command line what is already on disk. Both can now ask it, and the hub and the CLI can also ask the counterfactual — *what if the pool only granted this many slots?* — which is the question a reviewer actually has.
  - **The planner moved to `@blockingmachine/core`, and the extension kept only what is bundle-specific.** The catalogue, Chrome's limits, the ruleset validator, the capacity planner and the ledger attribution are pure — no `chrome.*`, no clock, no filesystem — so leaving them inside the extension meant the other two surfaces had to reimplement them, and three copies of a planner that decides what a user blocks is two too many. `shared/rulesetTiers.ts` is now a re-export plus `tierRuleCount`/`tierCompilationSource`, which read the file the packaging compiler writes and exist only inside a bundle; the capacity helpers bind that count in, and core takes its counts as an argument so the hub and the CLI can pass the numbers they read from the files in front of them. A fresh `./tiers` subpath export exists because the popup bundles: re-exporting the package root pulled core's node-dependent rule processing into the browser build and broke it.
  - **New `computeTierPlan` in core is the one implementation both surfaces run.** Reading the ledger, matching lines to tiers, validating the files and planning all live there; the CLI and the hub keep only what is theirs — getting bytes off disk and rendering. - **The Tier Plan Is Weighted by What Actually Blocked, Not by How Many Rules a Tier Ships (`@blockingmachine/browser-extension`)**:
  - The planner has accepted a per-tier `benefit` since it was written, and **nothing ever supplied one** — while the popup sat directly below it computing a ledger-graded *blocking card*. So the card graded tiers by what they blocked and the recommendation ranked them by size, and only the card said so. `benefitSource` was computed and then read by nothing at all: not the explanation, not the popup, not a test. The two disagreed about what a tier was worth, and the one the user was invited to *apply* was the one that did not know.
  - **`planTierBenefits` is the bridge, and it is mostly a refusal.** The obvious wiring — hand the planner each tier's hit count — is wrong in a way that only shows up once running: **a disabled tier's zero is not a measurement.** A tier that is switched off cannot block, so it accrues no matches, and a plan reading those zeros as worthless would rank every tier the user had deliberately turned *off* below every tier they had left on, and would then argue for re-enabling the ones they chose to disable. That is the switch wearing the costume of a measurement. So the gate asks whether a number *exists*, not whether it is large.
  - **The rule, stated as history rather than as a verdict.** A tier is measured if it has ever fired, or if it is currently on and the ledger has seen at least the 50 matches the blocking card already requires. A tier that fired 12 times and was then switched off counts, because switching a tier *off* keeps its history and only switching it *on* clears it — which is what makes the evidence basis reachable for anyone who has tried each tier once, instead of permanently closed to anyone who has ever turned anything off. An empty catalogue is refused too: "every tier is measured" is vacuously true of no tiers, and an empty benefit map would claim a measurement for a plan that does not exist.
  - **The benefit is raw blocks, not a rate.** The planner maximises a sum under a slot constraint, so the benefit has to be denominated in the thing being maximised; a rate would reward a tier for being small. Rule counts keep doing their job as the *cost* side of every comparison, which is how a 435-rule tier that earned its slots outranks a 1,800-rule tier that did not.
  - **Which basis produced the plan is now stated, twice, because "it ranked" is not a claim a user can check.** The plan's explanation carries a *Ranked by measured blocking* or *Ranked by rule count* line naming the units, and the new presentational `TierPlanBasis` sits under the plan with the reason — including *which tier* the ledger could not measure and why, so a plan that fell back is not silently indistinguishable from a plan that weighed the evidence and found it fine.

That is the gate working, not the feature failing.
  - 14 new tests (409 in the package, up from 395): the gate on every verdict, a retained history counting after a tier is switched off, an unobserved tier not reading as a zero, an empty catalogue, and — through the planner itself — coverage and evidence choosing opposite tiers on the same budget, a partial benefit set being ignored rather than blended, and the bridge's benefits reaching the plan end to end. - **The Tier Cut Is Decided by What Actually Blocked, Not by a Merged List's Concatenation Order (`scripts`, `@blockingmachine/browser-extension`)**:
  - MV3 guarantees an extension 30,000 static rules across its *enabled* rulesets and the Hub's list is ~122,801 hosts, so two thirds of what the user asked to block does not ship — and the compiler chose the survivors with `candidates.slice(0, take)`: pure input order. That is not a neutral tiebreak. A hub blocklist is a merge artifact, so its order is whichever upstream list was concatenated first, and the previous entry's ledger is the only body of evidence in the project that says which of these hosts *actually blocked traffic*. The compiler never read it. The 92,811 hosts that do not ship were therefore being discarded on the strength of a paste order.
  - **`--hits <file>` ranks each tier's candidates by the browser's own rule-hit evidence before the budget is allocated** — the same `<count> <rule>` ledger text `build-hot-list.mjs --hits` already reads, so a raw merged ledger and the hot list built from one are both valid input. - **The Hot Set's Evidence Can Be Real Usage, Not One Trace (`@blockingmachine/core`, `@blockingmachine/browser-extension`, scripts)**:
  - The hot set is only as honest as the measurement behind it, and the measurement was one captured trace from one machine. `build-hot-list.mjs` already had a `--hits` path for "a browser-reported rule-hit ledger (the honest one)" — but nothing produced one, and nothing in the file said what it covered. Both halves exist now: the extension accumulates the matches the browser actually applied, and `npm run ledger:merge` turns N session exports into the `<count> <rule>` ledger that build reads.
  - **Durability is days, not hits.** One busy afternoon of one site can out-count a rule that quietly fires every day for a month, and the hot set is supposed to hold what a user's traffic encounters — so a rule carries `count`, `sessions` and the distinct UTC days it fired on, and `minDays` is how a caller says "fewer rules that recur, rather than more that fired once". Three sessions inside one day is one day of evidence. A session that crosses midnight is **split into two**, because one date for hits that happened on two days would understate the evidence and make the day count depend on when a browser was opened.
  - **A firing exception is never a firing block.** An `@@` rule that allowed a request is accumulated on its own axis: counting it as a block would invert the rule's meaning and build a hot set out of the rules that did the least work.
  - **A match whose rule cannot be named is counted, not guessed at.** The filter text comes from loading the shipped rule files, which can fail; the session reports those as `unattributed` rather than inventing a rule, because a fabricated entry in this file becomes a fabricated entry in the hot set. The same rule applies to the format: a line that is only a number is refused, since `42` reads as a count with no rule *or* a one-hit pattern named `42`, and the two disagree.
  - **Order must not matter.** Sessions arrive in whatever order a directory listing or a retry produces, and the generated hot list is diff-checked — so the merge is commutative and the output is sorted (count descending, then rule text). An order-dependent build would fail that check on a machine that read its input differently. Both are pinned by a test that merges the same sessions forwards and backwards and compares the files.
  - The parser moved into core (`parseHitLedgerText`) and is shared with the exporter that writes the format, so there is one definition rather than a build script with its own copy of the rules — the same drift the tier catalogue check exists to catch. Provenance travels in the file's header, so the generated hot list states `browser-reported rule hits: 12 sessions across 34 days (2026-08-01 to 2026-09-03)` instead of "a browser-reported ledger", and a bare `<count> <rule>` file honestly reports no provenance rather than inventing one.
  - Verified end to end on real files: two exports, one of them containing an undated session, merged to `2 sessions across 2 days (2026-09-01 to 2026-09-02) · 3 blocking rules · 2 exceptions · 1 rejected as unusable`, and the build read the merged file and printed that provenance in its header.
  - 27 new tests (17 in core for the aggregation, 10 in the extension for the session tally), covering the busy-afternoon case, the midnight split, exceptions off the block axis, the cap keeping the most-fired rules, order-independence, round-tripping through the text format, and malformed input being counted rather than silently skipped.
  - **What is deliberately not wired: the background and popup glue.** No test in the extension touches `background/index.ts` and its setup has no `chrome` stand-in, so wiring a live-tally path there could not be verified — the same trap the removed `TrayManager` set. The module it will call is pure and tested, and the seam is named: resolve the match's filter (`staticRuleFilters.get(`${rulesetId}#${ruleId}`)`), record it, roll the tally at a UTC day boundary, flush to `chrome.storage.local` under `hitLedgerSessions`, and expose the export the popup downloads. Nothing half-wired ships.

- **Privoxy and BIND as First-Class Deploy Targets — and the Two Artifacts That Could Not Be Deployed (`@blockingmachine/core`, `@blockingmachine/cli`, `@blockingmachine/electron-app`, `packages/database`)**:
  - The Shadowrocket work ended by recording two formats as *not fixed*: `privoxy` (valid syntax, no target or recipe) and `bind` (no target or recipe **and** an artifact that cannot load). Both are closed here, and in both cases the artifact had to be repaired before there was anything worth documenting — which is why they were one piece of work rather than two documentation tickets.
  - **Privoxy's formatter emitted a section header per rule, with no pattern under it.** `{ +block { host } }` is an action block with an empty pattern list: the file loads and blocks nothing. Every rule now contributes only its own host pattern (`.example.com` — the leading dot is the mechanism, since a bare host in an action file matches that host alone), the single `{+block{Blockingmachine Blocklist}}` section is opened by the header generator before the first pattern, and the format is driven through the same DNS-precedence resolution as the other sinkhole formats.
  - **Ordering is part of the Privoxy format, and it is the opposite of Shadowrocket's.** The manual is explicit that when applying actions *the last action that matches a given URL wins*, so a child allow under a blocked parent is emitted in a `{-block}` section **after** the parent block it escapes — the exact reverse of the `DIRECT`-before-`REJECT` rule the Surge-style rule set needs.   - **A BIND master file does not comment with `#`.** The zone file's comment character is `;` — `#` is a parse error there — so the bind format picks its own comment prefix instead of the `# ` every other non-AdGuard format shares, and exception comments read `;`, not `#`. This is the kind of detail that produces a file that looks right in a diff and fails on the resolver.

- **Unbound Reachability: Proving the Drop-In Is Fetched and Loaded (`@blockingmachine/electron-app`)**:
  - The Unbound pane could tell a user their recipe was correct; it could not tell them whether anyone was following it, and the three failure modes are invisible from every other screen. A hub serving nothing, a scheduled `curl` that never runs, and an `include:` line that was never added all end with the resolver answering blocked names normally — which looks exactly like "no blocking configured".
  - New pure `src/unboundReachability.ts`. The third failure is observable, so it is tested directly: the canary is a domain taken *out of the artifact the resolver was just served* (`pickCanaryDomain` — shortest registrable name, because NXDOMAIN only proves sinkholing if the name would otherwise resolve), and `always_nxdomain` means NXDOMAIN proves the drop-in is loaded. A control query must resolve first, so a resolver that refuses names that should resolve is reported **inconclusive** rather than as a working blocklist, and a refused or timed-out query is **unreachable** rather than "not loaded". Verdicts name the fix: feed not answering, wrong format (`zones === 0`), nothing fetching, `include`/reload missing, resolver unreachable, no canary, or **stale** — blocking live with a copy older than the last compile, which is the difference between deployed and staying current.
  - The serve log is what answers "is anything fetching it": new `createFeedServeLog()` records every 2xx serve of a compiled file with peer, user agent and bytes, and the feed server feeds it. The check's own fetch is excluded by header (`reachabilityProbeHeaders()`) rather than by source address, because a resolver on this same machine connects from loopback *legitimately* and must still count — counting either one wrongly breaks the check in opposite directions.
  - **The canary is confirmed to exist before its NXDOMAIN is read as proof.** A domain that was never registered answers NXDOMAIN exactly like one the drop-in blocks, and the control query cannot tell those apart — it only rules out a resolver that refuses everything — so the same name is looked up on a reference resolver and the verdict turns on that answer: confirmed by a resolving reference is `live`, no reference (or one that cannot answer) is `canary-unconfirmed`, and a reference that *also* gets NXDOMAIN is `canary-nonexistent` — the check says it cannot tell rather than reporting a deployment as working on a name that does not resolve anywhere. `pickReferenceTarget()` prefers the address the user set, falls back to this machine's own configured resolvers, and refuses the resolver under test as its own reference (`::1` and `127.0.0.1` are one instance, not two), which is a configuration that can never confirm anything and is rejected at save time as well as at check time.
  - **The serve log is bounded per path, not just in total.** The hub serves several compiled files, so a browser extension polling `browser.txt` would push a single daily Unbound fetch out of a flat newest-200 window and the check would report "nothing has fetched it" for a deployment that fetched it an hour ago. Each path now keeps its own newest 25, with a total cap still keeping a scraped feed from growing the heap.
  - The resolver hint names the cost of the default rather than leaving the user to discover it: `127.0.0.1:53` is called a default the rows make visible, and when this machine resolves through something else, that address is offered as the thing to type.

Collapsing those is how a dead resolver gets reported as a working blocklist. The DNS call is injected, so the classification is tested without a socket.
  - Reading and checking are separate IPC calls: `get-unbound-reachability` returns the persisted verdict so opening the pane never fires a DNS query on tab switch, and `check-unbound-reachability` runs one on request. The last confirmed-live time and newest known fetch persist, so history survives a restart while the serve log deliberately does not — "has anything fetched this *since the hub started" is the question, and a remembered yes would be misleading.
  - Deploy Hub: new presentational `src/components/UnboundReachabilityCard.tsx` renders the verdict, the rows with per-row tone, the remedy, and an editable resolver address (persisted as `unboundResolver`, `127.0.0.1` by default, savable as `host`, `host:port` or a URL), with *Save* and *Check now*. A blank field falls back to `127.0.0.1:53` — the resolver the hub usually sits on — rather than refusing to check, and the hint says the address is a default; a typo is an error instead, because querying localhost for an address the user got wrong would produce a confident verdict about a resolver they never named. - **Coverage Measures the Rules the Browser Can Express, Not an Upper Bound (`@blockingmachine/core`, `@blockingmachine/cli`)**:
  - `blockingmachine coverage` reported its hit rate as `matched / indexedBlockingRules`, and neither half was the set the name implied. The denominator "everything the domain evaluator indexed" silently **included** path-preserving rules — `||cdn.example.com^*/ads.js` is indexed under its host, with the path discarded — and silently **excluded** initiator-scoped rules, because the evaluator's modifier guard skips `$domain=`. So a path rule read as a whole-zone block counted as a hit it had not earned: the rate was an upper bound, and the README called 118,218 rules "hostname-decidable" when they were not.
  - New pure `blockingRuleScope()` / `countRuleScopes()` in `packages/core/src/coverage.ts` classify every blocking network line into the four scopes the DNR compiler actually emits: `hostname` (a blanket host block), `initiator` (`$domain=`, `$from=`, `$to=`, `$third-party` — compiled to `initiatorDomains`), `path` (a kept path, `$path=`, or a regex — compiled to a URL pattern), and `request` (a request type or a response rewrite — compiled to `resourceTypes`). The buckets are exclusive with precedence `initiator`, then `path`, then `request`. Anything that is not a blocking network rule — comments, cosmetic and scriptlet lines, exceptions, `$badfilter`, DNS-only directives — returns `null`, so a list can be counted without pre-filtering it.
  - `isNetworkRule` now also drops AdGuard CSS injection (`#$#`, `#@$#`) and the `$@$` redirect form. They already met the module's own definition of cosmetic ("enforced by content scripts against the DOM, not against a request"); they simply were not recognised, so 4,637 DOM-injection lines were being counted as network rules.
  - The command reports all four counts, states the hit rate over the hostname-decidable bucket alone, and in a replay keeps context-scoped winners out of *both* the numerator and the denominator, reporting them as their own per-scope tallies with the requests they accounted for. The trace block still reports every request that was blocked, so "how much was blocked" and "how much of the decididable list fired" are separate answers rather than one blurred one. In `--hits` mode, where the ledger is browser-reported, the same split is applied to it.
  - Re-measured on the repository's own compiled export (249,751 lines) and the checked-in 11-page browsing trace: **118,379 hostname-decidable · 4,224 initiator-scoped · 7,628 path-scoped · 1,855 request-scoped** among 132,086 blocking rules (plus 4,106 exceptions). The session fires **70 of 118,379** (0.059%) rather than 71 of 118,218 — the rule that moved is a path-scoped one that won on 5 requests with its path never checked — the 95%/99% heads move from 65/70 to **64/69**, and dead weight is **99.941%**. Those figures are a floor, not a universal constant: the head of the list grows as coverage grows, the trace is eleven content-heavy pages from one machine, and it records requests as *attempted* — the sandbox refused several third-party hosts, and a refused connection still counts, which is what a network blocker sees anyway. A longer session would fire more rules.
  - 6 new core tests pin the four scopes, the precedence between them, the `null` cases and the list count, and the CLI suite gained the same split on a fixture, on a ledger, and on the real compiled list — asserting that the rate's denominator *is* the hostname bucket rather than a separately computed number that can drift from it. Two CLI tests that had pinned the old behaviour were rewritten rather than loosened: one is now named for keeping scoped winners out of the rate, the other for why the path rule no longer counts.
- **The Element Classifier's Prior Is Chosen by Cross-Validation, Not One Inner Split (`@blockingmachine/core`)**:
  - `selectPriorStrength` chose the regularisation strength on a *single* inner split of the training cases, so each candidate was fitted on roughly half the data it would finally see and validated on about a quarter. That measures the fit's starvation rather than the prior's value: unregularised looked catastrophic there (inner logLoss **1.18 against 0.34**) and a positive strength therefore always won, while the same unregularised fit generalised *better* than any regularised one once trained on the whole split (held-out logLoss **0.0877 against 0.1796**). The option `innerHoldoutEvery` is replaced by `folds` (default **5**): the training cases are split into deterministic, class-stratified folds, each grid point is scored on the held-out fold of every split, and the winner is refit on all of the training cases.
  - The selection re-ran and moved the shipped strength from **5 to 1**. Mean fold logLoss across the grid: `0` 1.0929, `1` **0.5813**, `2` 0.6028, `5` 0.6535, `10` 0.6600, `20` 0.6828, `50` 0.7020 — unregularised is now clearly the worst candidate on the corrected scale too. Because the data term is a class-balanced mean that sums to exactly one example per case, strength 1 means the hand-tuned centre is worth one labelled element against 77: the corpus outweighs it about **77:1**.
  - The artifact was regenerated (`npm run fit:element-weights`): corpus 117 (77 train / 40 holdout), mean held-out cross-entropy **0.1796 → 0.1443**, held-out accuracy **0.90 → 0.95**, 2 cases won and 0 regressions, end-to-end 117/117 unchanged.
  - The residual gap the old rule hid is recorded rather than tuned away: unregularised still generalises better on the 40 held-out cases (0.0877 against 0.1443), which the ~62-case folds are too small to see. Selecting on the held-out set would make it a fitted quantity, so strength 1 ships and the named fix for the gap is more labelled cases, not a better hyperparameter.
  - One user-visible consequence, caught by the extension suite rather than the corpus: an element the user has personally marked *hide* is labelled `Ad` by the previous table and `Annoyance` by this one. The action and confidence are unchanged (`hide`, 78%) — only the class name moves, because a `user-choice` verdict weights Ad, Tracker and Annoyance identically and the residual evidence decides between them (a hero banner is not really any of the three). The extension test that pinned `Ad` now pins the property it exists for instead — that the tuned verdict travels through the *shared* classifier instance — which also makes it insensitive to future re-fits.
- **Action-Level Calibration Is Scored Only Where the Model Acts (`@blockingmachine/core`)**:
  - `elementActionCalibrationPair` read a `leave` verdict's confidence as `1 − p(acting is right)`, but that number is a class probability — "84% sure this is Content" is not a claim about a counterfactual action. It is why action-ECE floored around 0.10, and why adding six confident leave-only cases moved it from 0.1016 to 0.1228 **for the hand-tuned reference and the fitted head alike**: the scale tracked corpus composition, not the weights.
  - It now returns `null` for a `leave` verdict, so the metric averages over the cases where the model actually acts — **63 of 117** — and the report prints the coverage beside the number (`acting calibration : ECE 0.044   Brier 0.006   (63 of 117 cases acted)`). Restraint, the question the old form was accidentally asking, is measured directly instead: `missedHides`, `undersoldHides` and the action mix (`61 hide, 2 suggest, 54 leave`).
  - On the corrected scale the two heads are close: reference ECE **0.0424**, shipped **0.0444** (delta +0.0020), Brier **0.0059 → 0.0062**. The old `< 0.1` absolute bar could not distinguish "unchanged" from "changed" — the reference sat one ten-thousandth under its own gate and no re-fit could beat it — so the test continues to state the guarantee as a regression bound against the reference, now with a 0.005 margin that reflects the corrected scale and a 0.02 absolute backstop.
  - `weightSetActionCalibration` in the fitting module was updated to match: it filters the `null`s and reports `scored`, so the harness and the shipping evaluation still measure the same quantity with the same code. A candidate judged by a private copy of a metric can pass a bar the product does not actually meet.

### Fixed
- **The Tier Block-Only Rule Was Asserted in the Suite but Not at the Release Gate (`@blockingmachine/browser-extension`)**:
  - `PRIORITY_STATIC_TIER` and `validateTierRuleset` have always required every tier rule to be a bottom-priority `block`, and a test walks the shipped tier files for both. The MV3 compliance script checked the priority but only that an action *existed*, never that it was a block — so the release gate and the suite were enforcing two different rules while the docs described one.
  - That gap was not cosmetic. Priorities are compared across every match, not just within a band, so a static `allow` at priority 2 beats a dynamic block at 1: a hand-edited or miscompiled tier could have shipped a ruleset that outranks the extension's own blocking, which is the exact failure the bottom band exists to prevent. The script now rejects any tier action that is not `"block"`, naming the reason, and its `STATIC_TIER_PRIORITY` comment spells out the cross-band comparison that makes block-only load-bearing rather than stylistic.
  - A new test pins the two implementations together, since neither imports the other: it asserts the compliance script still checks `action.type !== 'block'` and still declares `STATIC_TIER_PRIORITY` equal to `PRIORITY_STATIC_TIER`, so changing the module's band without changing the gate (or dropping the action check) fails instead of silently weakening a release.
- **Element Classifier Wrong on Five Live Pages: Five Defects, 33 Phantom Hides (`@blockingmachine/core`)**:
  - The element corpus is synthetic, so it only encodes the shapes someone thought of. The shipping scanner was run over **five real pages** (MDN, the Guardian front page, github.com, nytimes.com, Wikipedia) through the real collection path — the extension's own `isCandidateElement`/`snapshotElement`, compiled with the project's `tsc`, with only raw DOM facts read in the page and every decision made by the shipped `MiniAiElementClassifier`. Of 1,019 classifications, **109 were actionable and 52 were wrong**, 33 of them outright `hide` verdicts on things no one wants hidden. Full write-up in `docs/element-classifier-live-scan.md`.
  - **Destructive, and the single largest cause: a zero-area box was read as a 1×1 beacon.** `isPixel` was `width <= 4 && height <= 4` on *any* tag, and an unrendered `<script>`, a lazy photo that has not laid out and a collapsed ad slot all measure 0×0. That produced `Tracker/hide 98%` on MDN's own bundles, the Guardian's own asset host and its editorial photos, GitHub's bundles, NYT's `dd.nytimes.com` tags and **Wikipedia's own logo** — 33 verdicts across four of the five sites. Pixel geometry now requires a rendered box (`area > 0`) **and** a tag that can own one, and `details.pixelBox` carries the measured box so the reason string can no longer say "1×1" about a 0×0 element.
  - **A path-relative URL was parsed as a hostname.** `hostOfUrl` prefixed `https://` and stripped the leading slash, so `/static/client/runtime.js` resolved to the domain **`static`** and `/w/load.php` to **`w`**. Those invented hosts then read as "remote, not a CDN" and turned first-party assets into beacons. Relative references now yield no host; protocol-relative `//cdn.example/a.js` still resolves, because it does name one.
  - **A React-generated id named an ad.** GitHub's account menu carries `id="_R_ad_"`, whose fragments satisfied the compound-edge rule, so a working menu was **hidden at 98%**. Ids matching `GENERATED_ID_LIKE` (`_R_*`, `:r3:`, `radix-*`, `mui-*`, `headlessui-*`, `downshift-*`) now contribute no vocabulary. A first attempt also required both halves of a compound to be words, which broke the pinned `in-article-ad` case and was removed: the generated-id filter is the fix with direct evidence, and the extra net was an over-generalisation from one example.
  - **An analytics attribute was as strong as the word "tracker".** The prior rated `dataTrackerAttribute` at `+12` for Tracker (against `+13` for `trackerStrongToken`) and `−8` for Content, and modern pages put a `data-analytics-*`/`data-track-*` attribute on nearly every link — on github.com it was the entire difference between leaving a footer profile link alone and **suggesting it be blocked as a Tracker** (7 of the page's 14 verdicts). The attribute now counts only on an element that is already tracker-flavoured (tracking vocabulary, a measurement host, beacon or frame shape), and the prior rates it with `trackerWeakToken`. Corpus support was added and the weights refitted; a guard case keeps a real 1×1 beacon *with* an analytics attribute at `Tracker/hide`.
  - The fifth defect was a symptom, not a separate bug: the Guardian's `.top-fronts-banner-ad-container` was reported as **Tracker** on a rectangle whose own class says `ad`, because the bogus `pixel-shape` family is definitive and maps to Tracker, outranking the weak ad vocabulary actually present. It falls out of the first fix.
  - Six cases from these pages were added to the labelled corpus (GitHub footer link, `_R_ad_` menu, GitHub's own bundle, MDN's relative-src script, Wikipedia's logo, a lazy Guardian photo) plus the beacon guard, so the fixes are pinned by the corpus rather than by a reading of it. Result: **117/117** class-and-action correct for both the reference and the fitted table; held-out **0.90 → 0.95** accuracy, logLoss 0.2528 → 0.1796, 2 wins / 0 regressions. On the live pages, actionable verdicts went **109 → 53**: MDN 5 → 0, GitHub 14 → 0, Wikipedia 2 → 0, Guardian 62 → 42, NYT 26 → 11 — with every real detection kept (the Guardian's 40 DFP slots, `doubleclick`/`amazon-adsystem` loaders, `scorecardresearch` beacons, NYT's hidden `/ads/tpc-check.html` frame).
  - Two findings were recorded in the write-up instead of being acted on there, and both have since been fixed in their own change: the prior selection was measuring the fit's starvation rather than the prior's value, and the action-calibration metric was reading a class confidence as a probability of acting. See the two entries under **Changed**.
- **Element Classifier: Four Rules the Corpus Never Exercised (`@blockingmachine/core`)**:
  - The element evaluation corpus grew from **67 to 110 labelled cases**, built as the shapes real pages produce and the first pass never saw: Google Ad Manager's filled-slot attribute, `<amp-ad>`, the mobile anchor unit, outstream video, an ad slot on an unknown `ads.` host, a sponsored listing, New Relic and TikTok beacons, a `<dialog>`-based consent wall, an ARIA modal, a Quantcast `qc-cmp2` container, and twenty false-positive traps (`address`, `adobe`, `adjust`, `advisor`, `native`, `sponsored`, `role="banner"`, a user-invoked login modal, a plain `<video>` player). Most of the corpus grew because of what the six failures below turned out to be.
  - **Destructive:** the article-length shield was bypassed by *any* non-shape-only definitive family, so vocabulary counted as if it were a resource. `#advertising-policy` (1,288 characters of prose) was **hidden at 98%**, and `class="sponsored-article-body"` (2,760 characters) at 78% — a page *about* advertising wears the same class word as an ad slot. The shield now overrules vocabulary, `ad-ancestor`, and `push`/`nag` markers; only `ad-attribute` and `ad-network` evidence — a resource the page cannot be made of — can defeat it. It also determines the reported *class*, not just the action, so such an element is reported as Content rather than shown to the user as an Ad. A pinned overlay is exempt from the shield itself, because a modal is not the page it covers: a newsletter modal with pages of copy must still be a nag, which was caught by the existing suite when the first version of this change got it wrong.
  - The tag was not part of the identifier token scan, so `<amp-ad type="doubleclick">` produced one shape-only family and was **left alone at 52%**. A tag is an author's identifier and is where purpose-built elements say what they are; atom matching keeps `header`, `aside` and `figure` out of it, and `address`/`adapter` out of `ad`.
  - A compound identifier was no stronger than a bare one, so `class="video-ad"` scored exactly like `class="ad"` and an outstream video ad was only **suggested at 58%**. A compound that *leads or ends* with `ad`/`ads` now promotes to strong ad markup. Position is the entire guard: `no-ads-subscription` and `ads-free-upsell` name an upsell, and a middle atom never promotes — a corpus case pins that.
  - Push-notification opt-ins had no marker at all, so a pinned OneSignal prompt (`#onesignal-slidedown-container`, `z-index: 2147483647`) was reported as **page copy at 52%**. Push vendor containers and generic prompt ids joined the nag markers, and the sentence real prompts actually use joined the lure phrases.
  - Quantcast ships `qc-cmp2-*`, which the existing `cmp-container` marker could not match because of the version digit; `qc-cmp` was added, so a full-screen CMP that was reported as page copy now hides.
  - Two mislabelled corpus cases were corrected rather than the rules loosened: a pinned push prompt with *no* vendor marker hides on its copy plus its overlay shape (two independent hints), and `no-ads-subscription-cta` is expected Content/Annoyance at most since the model leaves it alone.
  - One existing assertion was deliberately rewritten: `element-ai.test.ts` pinned `header-ad` as a *weak* token, which is exactly the rule the video-ad case exposed as wrong. The test now separates the three cases that matter — a bare `ad` stays weak, a compound edge promotes, a middle atom does not.
  - Result: **110/110 class accuracy, macro F1 0.975, zero content destroyed, zero missed hides, zero undersold suggests**. Calibration was booked at **0.0999 against its own 0.1 gate** (0.073 at 67 cases) — a one-ten-thousandth margin, recorded in the test with the cause rather than quietly relaxed: the harness derived an expectation to act from `maxAction`, so every case the corpus merely *permitted* acting on was scored as a missed hide when the model correctly left it alone. That reading was wrong, and the metric has since been corrected along with the assertion — see the calibration entry under **Changed**.
- **Static Tiers Were Never Reconciled Against the Browser, Only Silenced (`@blockingmachine/browser-extension`)**:
  - `RulesetManager.setSuspended()` guarded its re-assert logic on `wasSuspended`, so calling it to *unpause* an extension that was not paused did nothing at all. The caller is `applyCurrentRules()`, which runs on every rule application and on every service-worker start — so it issued a `setSuspended(false)` that returned immediately, and the persisted selection was never asserted against the browser's own ruleset state.
  - The visible failure: Chrome resets an extension's enabled rulesets to the manifest defaults on update (only `tier_core` is declared enabled), so a user who had *Ad networks* and *Tracking & analytics* on would have storage still holding that choice while the browser blocked nothing. The popup reads the selection back out of storage, so it reported those tiers as enabled — the toggles said on, and nothing was blocking. The same drift follows disabling and re-enabling the extension.
  - Fixed by making the method reconcile in both directions and always read the browser first: while paused it disables whatever is actually on, and while unpaused it runs `sync()`, which issues no call when the two already agree. `sync()` was previously reachable only from a tier toggle and from a genuine pause→resume transition, and was never called from `background/index.ts` at all.
  - 3 new tests plus an extended one: a browser reset to the manifest defaults is repaired with no pause involved and without touching the saved selection; a browser that already matches gets no `updateEnabledRulesets` call, so the reconcile is cheap enough to run on every rule application; a browser that refuses to report its rulesets leaves the selection unasserted rather than guessing; and a selection changed *while* paused is what gets applied on resume.
  - Verified by regression: temporarily restoring the guard turned four tests red, including the new repair case, so the tests fail for the bug rather than merely passing alongside it.
- **Watchdog Re-Arm Killed the Reputation-DB Refresh Timer (`@blockingmachine/electron-app`)**:
  - Pasted-in timer cleanup inside `setupAiWatchdogTimer` cleared `dbRefreshTimer` on every invocation — each watchdog re-arm (which fires after every sweep with flagged traffic) would have silently stopped the hourly reputation-db hot-patch refresh. The stray block is removed and the function signature restored.
- **Heat Entries Lost Client Attribution (`@blockingmachine/electron-app`)**:
  - `recordRadarHeat` only propagated its optional `clientHint` parameter, dropping the per-result client collected by watchdog sweeps and live-radar polls. Per-result clients now fall back correctly when no hint is passed.
- **Feedback Reset Could Not Undo Zone-Generalized Whitelists (`@blockingmachine/core`)**:
  - `tuneDomainFeedback(domain, 'whitelist')` writes both an exact entry and a generalized registrable-zone entry, but `reset` only deleted the exact entry — leaving the zone bias active so `adserver.adtech.de` stayed force-whitelisted via the `adtech.de` fallback. Reset now also clears the zone entry.
