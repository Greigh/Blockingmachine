## [Unreleased]

### Added
- **The Hot Set's Evidence Can Be Real Usage, Not One Trace (`@blockingmachine/core`, `@blockingmachine/browser-extension`, scripts)**:
  - The hot set is only as honest as the measurement behind it, and the measurement was one captured trace from one machine. `build-hot-list.mjs` already had a `--hits` path for "a browser-reported rule-hit ledger (the honest one)" — but nothing produced one, and nothing in the file said what it covered. Both halves exist now: the extension accumulates the matches the browser actually applied, and `npm run ledger:merge` turns N session exports into the `<count> <rule>` ledger that build reads.
  - **Durability is days, not hits.** One busy afternoon of one site can out-count a rule that quietly fires every day for a month, and the hot set is supposed to hold what a user's traffic encounters — so a rule carries `count`, `sessions` and the distinct UTC days it fired on, and `minDays` is how a caller says "fewer rules that recur, rather than more that fired once". Three sessions inside one day is one day of evidence. A session that crosses midnight is **split into two**, because one date for hits that happened on two days would understate the evidence and make the day count depend on when a browser was opened.
  - **A firing exception is never a firing block.** An `@@` rule that allowed a request is accumulated on its own axis: counting it as a block would invert the rule's meaning and build a hot set out of the rules that did the least work.
  - **A match whose rule cannot be named is counted, not guessed at.** The filter text comes from loading the shipped rule files, which can fail; the session reports those as `unattributed` rather than inventing a rule, because a fabricated entry in this file becomes a fabricated entry in the hot set. The same rule applies to the format: a line that is only a number is refused, since `42` reads as a count with no rule *or* a one-hit pattern named `42`, and the two disagree.
  - **Order must not matter.** Sessions arrive in whatever order a directory listing or a retry produces, and the generated hot list is diff-checked — so the merge is commutative and the output is sorted (count descending, then rule text). An order-dependent build would fail that check on a machine that read its input differently. Both are pinned by a test that merges the same sessions forwards and backwards and compares the files.
  - The parser moved into core (`parseHitLedgerText`) and is shared with the exporter that writes the format, so there is one definition rather than a build script with its own copy of the rules — the same drift the tier catalogue check exists to catch. Provenance travels in the file's header, so the generated hot list states `browser-reported rule hits: 12 sessions across 34 days (2026-08-01 to 2026-09-03)` instead of "a browser-reported ledger", and a bare `<count> <rule>` file honestly reports no provenance rather than inventing one.
  - Verified end to end on real files: two exports, one of them containing an undated session, merged to `2 sessions across 2 days (2026-09-01 to 2026-09-02) · 3 blocking rules · 2 exceptions · 1 rejected as unusable`, and the build read the merged file and printed that provenance in its header.
  - 27 new tests (17 in core for the aggregation, 10 in the extension for the session tally), covering the busy-afternoon case, the midnight split, exceptions off the block axis, the cap keeping the most-fired rules, order-independence, round-tripping through the text format, and malformed input being counted rather than silently skipped.
  - **What is deliberately not wired: the background and popup glue.** No test in the extension touches `background/index.ts` and its setup has no `chrome` stand-in, so wiring a live-tally path there could not be verified — the same trap the removed `TrayManager` set. The module it will call is pure and tested, and the seam is named: resolve the match's filter (`staticRuleFilters.get(`${rulesetId}#${ruleId}`)`), record it, roll the tally at a UTC day boundary, flush to `chrome.storage.local` under `hitLedgerSessions`, and expose the export the popup downloads. Nothing half-wired ships.
- **What the Cascade Did With Each Verdict, Shown Where the Verdicts Are (`@blockingmachine/electron-app`)**:
  - The engine has recorded a `TriageOutcomeSummary` on every result of a cascade scan since the cascade shipped; the app's own `AiScanResult` declaration omitted the field, so the results list could not read it and the cascade's whole point — knowing *which* verdicts were screened locally, escalated, contested or deferred, and how undecided each one was — was only visible in the CLI report. The field is now declared, and each row in both Radar result lists carries the outcome and the ambiguity score that produced it.
  - New pure `src/triageDisplay.ts` and presentational `src/components/TriageOutcomeChip.tsx`, so the live list and the crawl list render one chip rather than two hand-written copies. Buckets are **action-plus-source, not action alone**, and the order is the contract: a contested verdict is a `source: 'contested'` escalation, and it is checked first because the disagreement is the more useful fact than the escalation it came with. An unrecognised action is `untracked` rather than falling through to a default — a bucket named after the engine's own vocabulary should not be assigned by elimination.
  - **A result with no cascade record renders no chip at all.** A greyed `SCREENED 0%` would be a fabricated outcome: absence of a record is not a decision, and `formatAmbiguity` returns null rather than `0%` for the same reason. The list header summarises the buckets only when at least one result carries a record, drops the zero `contested`/`deferred` counts (notable only when they happen), and always names the rows without a record, so a half-covered list cannot pass for a fully screened one.
  - **The false-positive guard turned out to be the main reason a running cascade leaves no record, and the first draft of the summary got it wrong.** Measured against the real service with the cascade enabled: `localhost`, `telemetry.vendor.example`, `cdn-magiclinks.trackonomics.net` and `mixed-signal.analytics.example` all return clean with **no** `triage`, because `isSafeInfrastructure` returns before the screening pass runs — 4 of 9 rows in one sample, 39 of 42 in another. A single "4 not screened" count read as a coverage gap in a list where the guard had deliberately skipped four domains, so the summary now separates the two causes (*cleared before screening* vs *without a cascade record*, in a split that stays exhaustive) and the chip's own vocabulary no longer claims the cascade was off.
  - **Contested is reachable but narrow, and this is the measurement rather than an assumption.** Across 51 sampled hostnames driven through the real engine against a stub model, three of the four buckets were produced end to end (`screened-locally`, `escalated`, `deferred`) and **none** was contested. The reason is structural: `assessAmbiguity` zeroes the score for a non-clean verdict carrying high-precision evidence (`decisive = highPrecision && nonClean && !conflicting`), so a name-backed tracker never escalates and never reaches the merge that can contest it. That left the window as a claim read off the source, so it is now **pinned by a test** in `triage-cascade.test.ts` with an explicit candidate — name-based evidence, conflicting contributions so `decisive` stays false, and enough live signals (near-tie plus the block/allow band) to clear the default bar — which asserts the assessment is ambiguous *and* that the merge then returns `contested` with the block kept. The bucket ships, and the path to it is a fact this repo now checks rather than a bucket someone could reasonably assume is decoration.
  - **The chip is legible on both themes, which it was not.** Contrast measured against each chip's composited background (its tint over the card) came out at **1.38–1.65:1** on the light theme — the tints were tuned for the dark surface while the default theme is `system`, so a first run in light mode was the *common* case. Light overrides darken each tone, and two dark-theme chips that measured under AA (grey labels at 3.95/4.31, contested at 4.40) were moved to shades that clear it: worst case is now **4.85:1 light, 4.58:1 dark**, with nothing below 4.5 on either theme. The measurements are in the CSS comments next to the values they justify.
  - **The cause is now recorded by core instead of inferred from a sentence.** `AiScanResult` gains an optional `falsePositiveGuard: { cleared, reason }`, written by `isSafeInfrastructure`'s early return. Without it the display decided what the engine had done by matching `'Protected by False Positive Guard'` inside `reasons` — it worked, but a reworded string in core would have silently reverted the summary to calling a deliberate skip "not screened", and a reader that reports coverage should not be parsing prose. The field is authoritative and validated by `isAiScanResult`; the sentence stays as the documented fallback, because readers already look for it and records cached across an upgrade predate the field. It is absent on every result the guard did not clear — pinned by a test, since a defaulted value would mark an entire scan as guard-cleared. `blockingmachine ai-scan` prints the same fact (`⊘ skipped — cleared by the false-positive guard`, with the guard's own reason) instead of jumping from the verdict to no `Triage Cascade` section at all.
  - 57 new tests, including a table of malformed and unknown records that must all read as `untracked` rather than as a guessed bucket, a table of malformed guard records that must not read as cleared, a render test that asserts a missing record produces no markup, and one that drives the **real** `AiDetectorService` (provider `mini-ai`, no network) to pin both the guard's field and its marker sentence — so a rewording in core fails the display test instead of silently reverting the summary to the vaguer claim it used to make.
  - Verified end to end rather than only from fixtures: temporary probes drove the real cascade against a stub Ollama and fed genuine records through the display layer — the four buckets' reachability above, the guard's zero-model-call path, and the header line on a real 9-row list (`3 screened locally · 1 escalated · 1 deferred · 1 model call (20.0%) · 4 cleared before screening`). Deleted afterwards.
- **Privoxy and BIND as First-Class Deploy Targets — and the Two Artifacts That Could Not Be Deployed (`@blockingmachine/core`, `@blockingmachine/cli`, `@blockingmachine/electron-app`, `packages/database`)**:
  - The Shadowrocket work ended by recording two formats as *not fixed*: `privoxy` (valid syntax, no target or recipe) and `bind` (no target or recipe **and** an artifact that cannot load). Both are closed here, and in both cases the artifact had to be repaired before there was anything worth documenting — which is why they were one piece of work rather than two documentation tickets.
  - **Privoxy's formatter emitted a section header per rule, with no pattern under it.** `{ +block { host } }` is an action block with an empty pattern list: the file loads and blocks nothing. Every rule now contributes only its own host pattern (`.example.com` — the leading dot is the mechanism, since a bare host in an action file matches that host alone), the single `{+block{Blockingmachine Blocklist}}` section is opened by the header generator before the first pattern, and the format is driven through the same DNS-precedence resolution as the other sinkhole formats.
  - **Ordering is part of the Privoxy format, and it is the opposite of Shadowrocket's.** The manual is explicit that when applying actions *the last action that matches a given URL wins*, so a child allow under a blocked parent is emitted in a `{-block}` section **after** the parent block it escapes — the exact reverse of the `DIRECT`-before-`REJECT` rule the Surge-style rule set needs. One shared ordering constant could not serve both formats, so each driver states its own.
  - **The BIND artifact could not be repaired in place.** BIND refuses to load a primary zone whose file has no SOA, and the formatter emitted one `zone "host" { type master; file "null.zone.file"; };` per blocked domain — a file that does not exist, in the core path, and `/dev/null` in the published one. No single master file can serve 100k different origins either, so the per-domain shape was not fixable: the artifact is now a **Response Policy Zone**, whose policy records *are* the list. `formatBindRule` emits `example.com CNAME .` (RPZ's documented NXDOMAIN reply), a child allow is `example.com CNAME rpz-passthru.` (resolved by longest match, so it needs no ordering at all), and the SOA/NS pair the BIND ARM itself uses is part of the header.
  - **A BIND master file does not comment with `#`.** The zone file's comment character is `;` — `#` is a parse error there — so the bind format picks its own comment prefix instead of the `# ` every other non-AdGuard format shares, and exception comments read `;`, not `#`. This is the kind of detail that produces a file that looks right in a diff and fails on the resolver.
  - **Both formats were unreachable from the CLI, and one of them from Settings.** `blockingmachine export` had no way to choose a format at all — it always wrote hosts, dnsmasq and adguard — so `--format privoxy,bind` was added (with an unknown name rejected rather than skipped), and the shared formatter now backs those two plus `domains` and `plain` instead of the silent raw-lines fallback. The CLI's own `SupportedFormat` was missing `domains` and `plain`, so widening it was a real fix rather than a formality.
  - New `packages/electron-app/src/privoxyDeploy.ts` and `src/bindDeploy.ts`: feed name and URL, the `actionsfile` line, the zone-stanza/`response-policy`/`rndc reload` trio, the format warning, the ordered setup steps and the syntax notes, all as data with the wording asserted. Two new Deploy Hub targets — **Privoxy** (feed URL, like Shadowrocket) and **BIND DNS** (a local zone file to copy, with no feed URL, because BIND cannot fetch one) — with the panes' registry entries, `case`s, Settings options and IPC acceptance. The additional-format writer now gives each artifact an extension that matches what it is (`.action`, `.rpz`) instead of a `.txt` holding a zone file.
  - `packages/database/scripts/update.js`, the standalone generator behind the published snapshots, wrote the same unloadable BIND stanzas; it now writes the RPZ records and the SOA preamble. **The 2025-04-23 snapshots committed under `packages/cli/filters/output/` are left as they are** — they predate every format fixed this session and are regenerated by the publication pipeline, not by hand, so rewriting 352,898 lines of stale output here would add a diff nobody can review to close nothing.
  - 36 new tests: the two core artifacts pinned in `advanced-formatter.test.ts` (the section opens before the patterns, dot-prefixed hosts, bypass-after-block, no `{ +block {` left anywhere; the SOA, `CNAME .` rather than a per-domain zone, `rpz-passthru.`, and that the file never comments with `#`), the formatter's own output in `formatters.test.ts`, the CLI writing both against the real command, 25 for the two deploy-helper modules, and the tier compiler's `--check` split into its two provenance cases.
- **`check:tiers` Now Checks Something, and `--format` Exists (`scripts/compile-tier-rulesets.mjs`, `@blockingmachine/cli`)**:
  - `npm run check:tiers` exited 1 on every machine and was therefore kept out of both the sweep and CI. The cause was a category error, not a stale file: the repository ships the **curated baseline** (24/36/36/22 rules) while any machine with a compiled hub list derives a **30,000-rule plan**, and `--check` compared the two unconditionally — so it reported "stale" for a tree that was exactly as intended.
  - The check is now provenance-aware. `tierCounts.generated.ts` is written by every run and is the declaration of which state the tree is in, so a recorded compilation still compares byte-for-byte against a fresh plan (which is the check that can catch a genuinely stale release), while the checked-in `null` baseline is verified on its own terms: every tier present, a non-empty ruleset array, and holding exactly the count `rulesetTiers.ts` declares for it — the catalogue the popup reports from. A hand-edit that adds a rule without moving the catalogue now fails; a clean checkout no longer does.
  - Verified both ways by perturbation, not assertion: appending one rule to `tier_core.json` fails the check with `holds 25 rule(s) but the catalogue declares 24`, and restoring the file (confirmed with `cmp`) returns it to green. The new behaviour is pinned in `tierCompiler.test.ts` with a synthetic catalogue, and `check:tiers` is now part of the CI "Verify generated artifacts" step, where it previously could not be run at all.
  - `blockingmachine export --format <list>` makes the CLI able to select its own output at all; before this it always wrote `hosts`, `dnsmasq` and `adguard`, which is what made `privoxy` and `bind` unreachable from the command line. An unknown name is an error rather than something silently dropped.
- **Unbound Reachability: Proving the Drop-In Is Fetched and Loaded (`@blockingmachine/electron-app`)**:
  - The Unbound pane could tell a user their recipe was correct; it could not tell them whether anyone was following it, and the three failure modes are invisible from every other screen. A hub serving nothing, a scheduled `curl` that never runs, and an `include:` line that was never added all end with the resolver answering blocked names normally — which looks exactly like "no blocking configured".
  - New pure `src/unboundReachability.ts`. The third failure is observable, so it is tested directly: the canary is a domain taken *out of the artifact the resolver was just served* (`pickCanaryDomain` — shortest registrable name, because NXDOMAIN only proves sinkholing if the name would otherwise resolve), and `always_nxdomain` means NXDOMAIN proves the drop-in is loaded. A control query must resolve first, so a resolver that refuses names that should resolve is reported **inconclusive** rather than as a working blocklist, and a refused or timed-out query is **unreachable** rather than "not loaded". Verdicts name the fix: feed not answering, wrong format (`zones === 0`), nothing fetching, `include`/reload missing, resolver unreachable, no canary, or **stale** — blocking live with a copy older than the last compile, which is the difference between deployed and staying current.
  - The serve log is what answers "is anything fetching it": new `createFeedServeLog()` records every 2xx serve of a compiled file with peer, user agent and bytes, and the feed server feeds it. The check's own fetch is excluded by header (`reachabilityProbeHeaders()`) rather than by source address, because a resolver on this same machine connects from loopback *legitimately* and must still count — counting either one wrongly breaks the check in opposite directions.
  - **The canary is confirmed to exist before its NXDOMAIN is read as proof.** A domain that was never registered answers NXDOMAIN exactly like one the drop-in blocks, and the control query cannot tell those apart — it only rules out a resolver that refuses everything — so the same name is looked up on a reference resolver and the verdict turns on that answer: confirmed by a resolving reference is `live`, no reference (or one that cannot answer) is `canary-unconfirmed`, and a reference that *also* gets NXDOMAIN is `canary-nonexistent` — the check says it cannot tell rather than reporting a deployment as working on a name that does not resolve anywhere. `pickReferenceTarget()` prefers the address the user set, falls back to this machine's own configured resolvers, and refuses the resolver under test as its own reference (`::1` and `127.0.0.1` are one instance, not two), which is a configuration that can never confirm anything and is rejected at save time as well as at check time.
  - **The serve log is bounded per path, not just in total.** The hub serves several compiled files, so a browser extension polling `browser.txt` would push a single daily Unbound fetch out of a flat newest-200 window and the check would report "nothing has fetched it" for a deployment that fetched it an hour ago. Each path now keeps its own newest 25, with a total cap still keeping a scraped feed from growing the heap.
  - The resolver hint names the cost of the default rather than leaving the user to discover it: `127.0.0.1:53` is called a default the rows make visible, and when this machine resolves through something else, that address is offered as the thing to type.
  - New `src/unboundProbe.ts`: `parseUnboundResolverAddress()` tolerates a bare host, `host:port`, an IPv6 literal, or a pasted URL; `queryUnboundResolver()` uses a one-attempt `resolve4` against the named server, and `classifyLookupFailure()` separates the three outcomes Node hides behind one rejection (`ENOTFOUND` = the sinkhole, `ENODATA` = the name exists so the drop-in is *not* loaded, timeouts and refusals = silence). Collapsing those is how a dead resolver gets reported as a working blocklist. The DNS call is injected, so the classification is tested without a socket.
  - Reading and checking are separate IPC calls: `get-unbound-reachability` returns the persisted verdict so opening the pane never fires a DNS query on tab switch, and `check-unbound-reachability` runs one on request. The last confirmed-live time and newest known fetch persist, so history survives a restart while the serve log deliberately does not — "has anything fetched this *since the hub started" is the question, and a remembered yes would be misleading.
  - Deploy Hub: new presentational `src/components/UnboundReachabilityCard.tsx` renders the verdict, the rows with per-row tone, the remedy, and an editable resolver address (persisted as `unboundResolver`, `127.0.0.1` by default, savable as `host`, `host:port` or a URL), with *Save* and *Check now*. A blank field falls back to `127.0.0.1:53` — the resolver the hub usually sits on — rather than refusing to check, and the hint says the address is a default; a typo is an error instead, because querying localhost for an address the user got wrong would produce a confident verdict about a resolver they never named. The card is render-tested through `react-dom/server`, including the snapshot-only state the pane is in every time it opens.
  - **Verified end to end against real I/O, not only fixtures:** temporary probes stood up an HTTP server serving a real drop-in and hand-built DNS servers, and the full pipeline classified them — the probe's own fetch absent from the serve log while the unmarked one was recorded, `ENOTFOUND` read as the sinkhole, a `stale` verdict when the compile was newer than the fetch, `not-loaded` when the resolver answered normally, `resolver-unreachable` on a refused connection, `inconclusive` when the control did not resolve, and — with two DNS servers — `live` from a reference that resolves the canary and `canary-nonexistent` from a reference pointing at the resolver under test. Deleted afterwards.
  - **The build caught a module boundary, which is the only reason it is in this entry:** the reference helper started in `unboundProbe`, and the Deploy Hub's renderer needs it for the hints — so the renderer bundle tried to resolve `dns/promises` and the webpack build failed. The pure address work now lives in `src/unboundAddress.ts` (no `dns` import), leaving `unboundProbe` with the query. Aliasing `dns` to `false` would have hidden it until the first call.
  - 73 new tests (31 classification and serve log, 16 addresses and reference choice, 7 probe, 9 render, 10 hint text), including that the probe cannot manufacture its own evidence, that the serve log stays bounded and per path, that a resolver which NXDOMAINs the control is not read as success, that an unconfirmed canary is never reported as live, that a deployment cannot be its own reference in any spelling of loopback, and that staleness is never claimed when the fetch cannot be dated.
- **Shadowrocket as a First-Class Deploy Target (`@blockingmachine/electron-app`, `@blockingmachine/core`, `@blockingmachine/cli`)**:
  - The audit that followed the Unbound work turned up three formats with the same gap: `privoxy`, `shadowrocket`, and `bind` are all emitted, advertised in the CLI examples, and published as subscribe URLs, yet none has a deploy target in the Hub, a setup recipe anywhere, or a row in the README's format table. Shadowrocket was the one to close first — it has by far the largest user base, and unlike the other two its syntax is the syntax its client actually wants.
  - **The artifact had to be fixed before it could be documented, because it was not deployable either.** The export emitted a bare list of rules with no `[Rule]` section for the app to read them out of, used `!` AdGuard comments in the CLI path where a Shadowrocket config expects `#`, and — the real defect — emitted `DOMAIN,host,REJECT`, the *exact-host* form, so every subdomain of a blocked domain was missed. It is now `DOMAIN-SUFFIX`, under a `[Rule]` section, with `#` comments, in both core header generators and both CLI paths.
  - **Ordering is part of the format.** A Shadowrocket/Surge rule set is evaluated top-down and first match wins, so a child exception under a blocked parent is now emitted as `DOMAIN-SUFFIX,child,DIRECT` *before* the parent's `REJECT` — the job dnsmasq's per-zone specificity and Unbound's `transparent` zone do by construction, and the one thing a copy of the list could get silently wrong.
  - New `packages/electron-app/src/shadowrocketDeploy.ts`: the feed filename and URL, the warning naming the current format when the export would write something else, the four setup steps as data, and the `DOMAIN-SUFFIX` syntax note. A **Shadowrocket** tab in the Deploy Hub renders them, and the format is selectable in Settings and accepted by the IPC validator, without which the tab could only ever point at a file the app cannot produce.
  - The platform tab strip now wraps; nine tabs no longer fit one row of `nowrap` labels.
  - 17 new tests: 12 for the deploy helpers (feed name and URL, the placeholder host, the format warning, the step contract, the syntax note), 4 pinning the artifact in `advanced-formatter.test.ts` (the section header precedes the rules, `DOMAIN-SUFFIX` rather than `DOMAIN,`, bypass before parent block, an allowlisted domain absent but explained), and 1 CLI export test against the real command.
  - **Recorded here, closed below:** `privoxy` (valid syntax, no target or recipe) and `bind` (no target or recipe *and* an artifact that cannot load — its master zones point at `/dev/null` in the published file and a nonexistent `null.zone.file` in the core formatter, and BIND refuses a master zone whose file has no SOA) were left as their own piece of work rather than smuggled into this one, and the entry above does that work: `bind` took the design decision it needed (a Response Policy Zone, because the per-domain shape cannot load at all).
- **A Block-Ledger Source Readout, With Its Polling Quota (`@blockingmachine/browser-extension`)**:
  - The per-tab counts in the popup come from two different browser APIs, and they are not equivalent: `onRuleMatchedDebug` reports every match live with its request URL, but only to unpacked builds, while `getMatchedRules` works packed at the cost of batching, withholding the URL, and a hard rate limit. Nothing in the UI said which one was feeding the ledger, so a count looked the same either way — and a polled ledger that had simply burned its quota looked exactly like a page that blocked nothing.
  - New pure `src/shared/ledgerStatus.ts`: `ledgerFeedFromAvailability()` picks the path the browser will actually use (live wins, since it is strictly better), and `formatLedgerQuota()` renders a budget that reads correctly in all three states — a full budget is not "0 used", a partial one names what is left, and an exhausted one names when the next call becomes legal rather than showing a bare zero.
  - New `matchedRulesQuotaView()` in `src/background/matchedRules.ts`, computed from the *same* call log `canRequestMatchedRules` gates on so the number the popup reports is the number that decides the next poll. New `GET_LEDGER_STATUS` message (a synchronous read of in-memory state, so it answers even while the quota is spent), and a presentational `src/popup/LedgerStatusCard.tsx` rendered in the popup's Hub tab — live/polled/off badge, the match source, the remaining quota, and a detail line naming the API and its cost.
  - 23 new tests (13 for the pure status module, 5 for the quota arithmetic, 5 render tests for the card): the feed pick when both paths exist, the badge tone and API naming per path, the three quota phrasings plus the reset duration and a nonsensical negative reading, `describeLedger`'s one-liner, and that the view `agrees with the gate it exists to explain`. The card is render-tested through `react-dom/server`, including that it shows no rows before the first read comes back.
- **A Coverage-Derived Hot Set, Shipped and Proved (`@blockingmachine/core`, `@blockingmachine/cli`)**:
  - The coverage work ended on a measurement with nowhere to go: the report said a real session fires ~70 of 118,000 rules — read that as a *floor* for a session, since the head of the list grows as coverage grows — and then nothing shipped that fact. `npm run build:hotlist` now turns a measurement into a list: it keeps the rules the measurement saw **fire**, plus the exception rules that fired, and writes `packages/cli/filters/output/hotlist.txt` with a header stating exactly what it cost. `npm run check:hotlist` fails if the file drifts from a fresh derivation, and CI runs it after the build.
  - New pure `selectHotList()` / `formatHotList()` in `packages/core/src/coverage.ts`, sharing `minimumRulesForShare` with the coverage curve so "the head that carries 99%" means the same thing in both places. Two properties make the result safe to stand in for a bigger list on the traffic it was measured on: only rules that *won* a request are included (so every blocked host still matches its winner and every untouched host still matches nothing), and a rule is only shipped if the source list actually carries it (so a stale ledger cannot inject one). Exceptions are kept for the same reason — dropping a fired allow rule would make the trimmed list block *more* than the one it replaced.
  - New `replayRuleHits()` in `packages/core/src/ruleReplay.ts`. The CLI's trace report and the hot-set builder now derive their hits from one implementation instead of two: a hot set built by a different loop than the one that measures it is a hot set nobody has checked.
  - `blockingmachine coverage --hot` measures the trimmed list instead of the full export, and the missing-list failure now points at it. It is opt-in on purpose: a report measured against 77 rules answers a different question from one measured against 118,000, and the caller should be the one to ask it.
  - **Proved with the existing measurement.** Against the same 11-page trace the full export blocks **132 requests on 85 hosts** while allowlisting 11 hosts through 6 exception rules; so does the 77-rule hot set, with the *same* rules deciding them — and 100% of its rules firing against 99.941% dead weight in the export. What the trace is, it now says: eleven pages from one machine, content-heavy, recording requests as *attempted* (the sandbox refused connections to several third-party hosts, and a refused connection still counts — which is what a network blocker sees anyway). So both figures are floors rather than constants: a longer session exercises more of the source list and adds hot rules, and the generated header states that.
  - **The limit is measured, not footnoted.** Deriving a hot set from half the session's pages and measuring it on the other half keeps only **38 of 93 blocks (40.9%)**, pinned in the test. A per-session hot set is exact for the traffic it came from and loses most of what it has never seen, so it ships as an opt-in trimmed default for a budget that cannot hold the full list — with the limitation printed in its own header — never as a replacement for the full export. - **Coverage Measures the Rules the Browser Can Express, Not an Upper Bound (`@blockingmachine/core`, `@blockingmachine/cli`)**:
  - `blockingmachine coverage` reported its hit rate as `matched / indexedBlockingRules`, and neither half was the set the name implied. The denominator "everything the domain evaluator indexed" silently **included** path-preserving rules — `||cdn.example.com^*/ads.js` is indexed under its host, with the path discarded — and silently **excluded** initiator-scoped rules, because the evaluator's modifier guard skips `$domain=`. So a path rule read as a whole-zone block counted as a hit it had not earned: the rate was an upper bound, and the README called 118,218 rules "hostname-decidable" when they were not.
  - New pure `blockingRuleScope()` / `countRuleScopes()` in `packages/core/src/coverage.ts` classify every blocking network line into the four scopes the DNR compiler actually emits: `hostname` (a blanket host block), `initiator` (`$domain=`, `$from=`, `$to=`, `$third-party` — compiled to `initiatorDomains`), `path` (a kept path, `$path=`, or a regex — compiled to a URL pattern), and `request` (a request type or a response rewrite — compiled to `resourceTypes`). The buckets are exclusive with precedence `initiator`, then `path`, then `request`. Anything that is not a blocking network rule — comments, cosmetic and scriptlet lines, exceptions, `$badfilter`, DNS-only directives — returns `null`, so a list can be counted without pre-filtering it.
  - `isNetworkRule` now also drops AdGuard CSS injection (`#$#`, `#@$#`) and the `$@$` redirect form. They already met the module's own definition of cosmetic ("enforced by content scripts against the DOM, not against a request"); they simply were not recognised, so 4,637 DOM-injection lines were being counted as network rules.
  - The command reports all four counts, states the hit rate over the hostname-decidable bucket alone, and in a replay keeps context-scoped winners out of *both* the numerator and the denominator, reporting them as their own per-scope tallies with the requests they accounted for. The trace block still reports every request that was blocked, so "how much was blocked" and "how much of the decididable list fired" are separate answers rather than one blurred one. In `--hits` mode, where the ledger is browser-reported, the same split is applied to it.
  - Re-measured on the repository's own compiled export (249,751 lines) and the checked-in 11-page browsing trace: **118,379 hostname-decidable · 4,224 initiator-scoped · 7,628 path-scoped · 1,855 request-scoped** among 132,086 blocking rules (plus 4,106 exceptions). The session fires **70 of 118,379** (0.059%) rather than 71 of 118,218 — the rule that moved is a path-scoped one that won on 5 requests with its path never checked — the 95%/99% heads move from 65/70 to **64/69**, and dead weight is **99.941%**. Those figures are a floor, not a universal constant: the head of the list grows as coverage grows, the trace is eleven content-heavy pages from one machine, and it records requests as *attempted* — the sandbox refused several third-party hosts, and a refused connection still counts, which is what a network blocker sees anyway. A longer session would fire more rules.
  - 6 new core tests pin the four scopes, the precedence between them, the `null` cases and the list count, and the CLI suite gained the same split on a fixture, on a ledger, and on the real compiled list — asserting that the rate's denominator *is* the hostname bucket rather than a separately computed number that can drift from it. Two CLI tests that had pinned the old behaviour were rewritten rather than loosened: one is now named for keeping scoped winners out of the rate, the other for why the path rule no longer counts.
- **The Element Classifier's Prior Is Chosen by Cross-Validation, Not One Inner Split (`@blockingmachine/core`)**:
  - `selectPriorStrength` chose the regularisation strength on a *single* inner split of the training cases, so each candidate was fitted on roughly half the data it would finally see and validated on about a quarter. That measures the fit's starvation rather than the prior's value: unregularised looked catastrophic there (inner logLoss **1.18 against 0.34**) and a positive strength therefore always won, while the same unregularised fit generalised *better* than any regularised one once trained on the whole split (held-out logLoss **0.0877 against 0.1796**). The option `innerHoldoutEvery` is replaced by `folds` (default **5**): the training cases are split into deterministic, class-stratified folds, each grid point is scored on the held-out fold of every split, and the winner is refit on all of the training cases.
  - The selection re-ran and moved the shipped strength from **5 to 1**. Mean fold logLoss across the grid: `0` 1.0929, `1` **0.5813**, `2` 0.6028, `5` 0.6535, `10` 0.6600, `20` 0.6828, `50` 0.7020 — unregularised is now clearly the worst candidate on the corrected scale too. Because the data term is a class-balanced mean that sums to exactly one example per case, strength 1 means the hand-tuned centre is worth one labelled element against 77: the corpus outweighs it about **77:1**.
  - The artifact was regenerated (`npm run fit:element-weights`): corpus 117 (77 train / 40 holdout), mean held-out cross-entropy **0.1796 → 0.1443**, held-out accuracy **0.90 → 0.95**, 2 cases won and 0 regressions, end-to-end 117/117 unchanged.
  - The residual gap the old rule hid is recorded rather than tuned away: unregularised still generalises better on the 40 held-out cases (0.0877 against 0.1443), which the ~62-case folds are too small to see. Selecting on the held-out set would make it a fitted quantity, so strength 1 ships and the named fix for the gap is more labelled cases, not a better hyperparameter.
  - One user-visible consequence, caught by the extension suite rather than the corpus: an element the user has personally marked *hide* is labelled `Ad` by the previous table and `Annoyance` by this one. The action and confidence are unchanged (`hide`, 78%) — only the class name moves, because a `user-choice` verdict weights Ad, Tracker and Annoyance identically and the residual evidence decides between them (a hero banner is not really any of the three). The extension test that pinned `Ad` now pins the property it exists for instead — that the tuned verdict travels through the *shared* classifier instance — which also makes it insensitive to future re-fits.
- **Action-Level Calibration Is Scored Only Where the Model Acts (`@blockingmachine/core`)**:
  - `elementActionCalibrationPair` read a `leave` verdict's confidence as `1 − p(acting is right)`, but that number is a class probability — "84% sure this is Content" is not a claim about a counterfactual action. It is why action-ECE floored around 0.10, and why adding six confident leave-only cases moved it from 0.1016 to 0.1228 **for the hand-tuned reference and the fitted head alike**: the scale tracked corpus composition, not the weights.
  - It now returns `null` for a `leave` verdict, so the metric averages over the cases where the model actually acts — **63 of 117** — and the report prints the coverage beside the number (`acting calibration : ECE 0.044   Brier 0.006   (63 of 117 cases acted)`). Restraint, the question the old form was accidentally asking, is measured directly instead: `missedHides`, `undersoldHides` and the action mix (`61 hide, 2 suggest, 54 leave`).
  - On the corrected scale the two heads are close: reference ECE **0.0424**, shipped **0.0444** (delta +0.0020), Brier **0.0059 → 0.0062**. The old `< 0.1` absolute bar could not distinguish "unchanged" from "changed" — the reference sat one ten-thousandth under its own gate and no re-fit could beat it — so the test continues to state the guarantee as a regression bound against the reference, now with a 0.005 margin that reflects the corrected scale and a 0.02 absolute backstop.
  - `weightSetActionCalibration` in the fitting module was updated to match: it filters the `null`s and reports `scored`, so the harness and the shipping evaluation still measure the same quantity with the same code. A candidate judged by a private copy of a metric can pass a bar the product does not actually meet.
