# The ledger dropbox

`ledger-hits.txt` in this directory is the accumulated evidence the shipped cut is ranked by.

It is a **dropbox**: the extension accumulates rule hits locally, someone exports them, and the
merge is committed here. Everything downstream of it — the extension's static ruleset tiers and
the CLI-served hot set — is re-derived from this file, weekly and automatically, by
`scripts/weekly-tier-compile.sh` on the schedule in `.github/workflows/weekly-tier-compile.yml`.

## Why the cut needs evidence at all

The extension ships static rulesets under Manifest V3's 30,000-rule guaranteed minimum, and the
hub's compiled list is ~117,000 domains. So *which* 30,000 rules ship is the entire decision, and
`compile-tier-rulesets.mjs` takes candidates in input order unless it is given `--hits`. Input
order in a merged blocklist is a merge artifact: whichever upstream list was concatenated first
gets the slots. That is a statement about how the list was built, not about anyone's traffic.

`--hits` ranks each tier's candidates by measured rule hits before the budget is allocated. Hosts
with evidence ship first, most-fired first; the rest keep their input order. It ranks *within* a
tier and never re-tiers, and the curated baseline keeps its place either way.

## What is and is not in here

The ledger is `<count> <rule>` — a blocklist rule and how many times the browser blocked with it.

It is **not** a browsing history. No URLs, no page titles, no timestamps, no initiator, no
request paths. `merge-browser-ledger.mjs` reads rule text and counts out of each session export
and drops the rest, and the merged file is all that is committed. That is a deliberate reduction:
the accumulation is what the cut needs, and a raw session export carries per-day timestamps that
would be a behavioural record rather than a blocklist statistic.

Even so, a real ledger says something about a person's browsing — which is worth a thought before
contributing one to a public repository. The alternative is the local-only route below.

## Adding to it

1. **Export.** In the extension popup, the hit-ledger card has an export button. It downloads
   `blockingmachine-hit-ledger-YYYY-MM-DD.json`, holding up to 50 of your recorded days. Export
   whenever you remember; once a month is plenty, since the merge keeps every day you give it.

2. **Merge.** Point `--from` at the folder the downloads landed in:

   ```
   npm run ledger:merge -- --from ~/Downloads
   ```

   That reads every `.json` in the directory in name order, merges them, and rewrites this file.
   Re-running with the same exports produces the same bytes — which is what lets the weekly job
   treat a diff as a real change rather than noise.

   To merge without writing, add `--out /tmp/scratch.txt`. To merge only some days, use repeated
   `--in <file>` instead of `--from`.

3. **Commit it.** The derived artifacts are regenerated by the weekly job, so this file is the
   only thing to commit.

## Running the weekly derivation yourself

```
scripts/weekly-tier-compile.sh
```

It rebuilds the hot set from this ledger, compiles the tier plan from it, checks the cut still
fits the MV3 budget, and verifies the shipped files match. It changes the tier files in the
working tree only to prove the compile works, then puts them back — the repository keeps the
curated baseline and compiles at package time. It refuses to run if it would discard tier changes
you made yourself.

With this file empty it does nothing and says so. That is the correct behaviour, not a failure:
there is no evidence to derive from yet.

## Keeping it off the public repository

The local runner is the same script. Point it at an export directory on a schedule and nothing has
to be committed at all:

```
launchctl load ~/Library/LaunchAgents/com.blockingmachine.ledger.plist
```

A working plist is in [`local-runner.plist`](local-runner.plist); edit the two paths and load it.
It runs `ledger:merge` against a directory of exports and nothing else — it does not compile,
does not commit, and does not touch the repository's derived files.

To ship a hot set derived from *your own* traffic on a hub you run — rather than this
repository's scripted sessions — the merge step can be skipped entirely. Point the derivation at
the export directory itself and it merges inline:

```
node scripts/build-hot-list.mjs --list <the list you serve> --sessions ~/Downloads \
  --out <the directory you serve>/hotlist.txt --write
```

The file's `Derivation:` header records the sessions paths, so `--check` against it later
re-derives from your exports, not from this ledger.
## What is in here now, and who put it there

`ledger-hits.txt` is **no longer empty**. It was produced by
[`scripts/ledger-browser-run.mjs`](../scripts/ledger-browser-run.mjs), which drives a real Chrome
with the unpacked extension, browses a scripted list of pages, and exports what the extension's own
static rules blocked. Four runs — three of 46 pages and one of 20, 158 pages in total — merged by
`ledger:merge`.

Read this before reading the numbers:

- **It is not a person's browsing.** The site list is the script's — chosen for third-party density —
  and the run is automated. Every hit in it is a real rule firing on a real page; none of it is
  anyone's history.
- **It is still not a browsing history.** The file records `<count> <rule>` and nothing else: no URL,
  no page title, no timestamp, no initiator, no client. That is the whole claim of this directory and
  the script does not weaken it.
- **The machine runs two upstream DNS blockers.** AdGuard on the host, and AdGuard Home on the LAN.
  Neither can *add* a match — a request the extension blocks is decided by its rules before any
  lookup happens, so an upstream resolver never sees it. Both can *remove* third-party traffic from
  the pages, so these totals are lower than the same pages would produce on a clean network. The
  ranking between rules is unaffected; the absolute volumes are not.
- **Every shipped tier was enabled for the run.** A fresh install enables `tier_core` alone, and a
  rule that is not installed cannot match: the first run of this produced 16 distinct rules, all of
  them `tier_core`, which would have been a ledger that says nothing about the five tiers the tier
  plan weighs. The script now turns the whole set on and verifies it before the first page loads.
- **One day, four sessions.** Recurrence across days is what a ledger is for, and a single
  automated afternoon cannot supply it. It ranks rules by what fired; it says nothing about what
  keeps firing.
- **Only one session carries the browser's own tier split.** The per-tier tally was added to the
  export after the first three runs, so their `tiers` in `session-*.meta.json` were reconstructed by
  matching each rule back to the tiers that ship its host — the `readTierLedger` arithmetic, which
  credits a host two tiers share to both. Session-d names the ruleset that won, which is exact, and
  the merged file states the coverage rather than blending the two: `# Tier sessions: 1 of 4`.

Per-run detail — the page list, the per-tier split and the same notes — sits beside each export as
`ledger/session-*.meta.json`.
