## Locked preconditions (verified in tree)

- `VpnFilterService.kt` already carries the two postures this plan straddles: DNS-only (narrow `/32` route to the virtual resolver) and hub capture (broad `0.0.0.0/0` + `::/0` routes → `TcpDispatcher` pair → `HubUpstream` PROXY-v2 splice to `<hub>:9294`, `DirectUpstream` pass-through relay for everything else, `UdpDispatcher`, counted UDP/443 drop). The `upstreamFactory` seam on `TcpDispatcher` is the whole injection point — engine mode is a third `SessionUpstream` dialing a LOCAL listener; `Packet`/`TcpSession`/reassembly/LRU don't change at all.
- The PROXY-v2 contract is transport-agnostic: `ProxyV2.encode` emits the real 5-tuple + optional `0xE0` auth TLV ahead of the stream — byte-identical whether the far end is a LAN hub or a listener inside the same process. Only the socket target changes.
- `packages/https-filter`'s Node-API surface is known and bounded: `net`, `tls`, `http`, `http2` (`terminate.ts` speaks real h2), `crypto`, `zlib`, `fs`/`fs/promises`, `stream`, `events`, `url`, `util`, `os`, `path`, `child_process` (keyWrap backends ONLY), plus vendored `node-forge` (x509 + RSA-2048 keygen — defers to `crypto.generateKeyPair` where a real `node:crypto` exists) and `@blockingmachine/core`'s `evaluateRequest`/`createCosmeticIndex` (pure TS — `coverage`/`RuleProcessor`/`ruleSyntax`/`entropy` carry no `node:` imports). No `worker_threads` and no `async_hooks` anywhere — `leafForgeQueue` deliberately serializes synchronous forge on the event loop with `setImmediate` yields between mints, so threading-model support is NOT a runtime-selection constraint.
- `FilterProxyConfig` already exposes every seam this plan needs: `keyWrapBackend` injectable (`KeyWrapBackend` = async `load`/`store` of a 32-byte wrap secret — no platform probing required by callers that inject), `bindHost`/`controlBindHost` split, `injectionBudget`, `rulesPath`, `storeDir`, and the `policyDegraded` ephemeral-ledger fallback.
- CA surfaces already built for the hub flow transfer verbatim to a device CA: `sha256.ts` (dependency-free SHA-256), `fingerprintOfPem`/`pemToDer`, the `PairedCa` store shape (`bm.httpsCapture.pairedCaPem`/`pairedCaSha256` — stored PEM re-verified against stored fingerprint on read), `LocalVpn.installCaCertificate` (the legit `KeyChain.createInstallIntent` path), and the confirm-dialog flow in `HttpsCaptureCard.confirmCaInstall`.
- The rules artifact question is real, not assumed: the engine's `BM_RULES_PATH` wants the FULL request-rules file (`browser.txt` — path rules, `$removeparam`, `##`/`#@#` cosmetic, `#%#//scriptlet`), while `syncRuleset` today pulls `/dns.txt` (domain-only) into three artifacts (`ruleset.txt`, `ruleset_native.txt`, `ruleset.meta.json` + the iOS app-group mirror). The feed server (`:9191`) already serves `browser.txt` — `feedServing.ts`'s allowlist carries it.
- Flag 126's platform ceiling is inherited verbatim: user CAs reach browsers + opted-in apps only; SNI-level verdicts cover every app regardless. The on-device engine changes WHERE verdicts happen, not WHICH apps can be content-filtered.
- Nothing P4 shipped is removed: `HubUpstream`, `BM_DATA_TOKEN`/`0xE0` TLV, `HubHost.requireLiteral`, sticky `hubToken`/`hubPort` extras, the paired-CA store, per-app bypass (flag 128) — the hub splice becomes the fallback leg, kept whole.

## JS runtime decision (the load-bearing choice, made honestly)

Three tracks were evaluated against the engine's actual dependency list above — TLS termination (`node:tls` with real OpenSSL), `node-forge` leaf signing (native `crypto.generateKeyPair`), `http2`, `zlib`, fs/store IO — not against vibes.

- **nodejs-mobile — the reference pick.** Real Node 18.20.4 (bundled OpenSSL 3.0.13), so EVERY `node:` API the engine touches exists — including `http2` and `crypto.generateKeyPair`, which is what makes node-forge's RSA path fast enough on-device. Costs recorded honestly: Janea Systems stepped back years ago; a sole maintainer (Open-Collective funded) ships when capacity allows — latest core release is v18.20.4 on the Node 18 line whose upstream EOL was 2025-04, so OpenSSL/V8 CVE drift is a standing risk to flag, not a blocker for an embedded runtime with no third-party code execution. Two build-floor items must verify at T1, not be assumed: Google Play's 16KB page-size requirement (nodejs-mobile PR #154 merged but no released AAR carries it — build from source if the published artifact isn't aligned) and the New-Architecture gap (`nodejs-mobile-react-native` is legacy-arch and dead under Expo SDK 58 — so we embed the CORE AAR's `libnode` + Java `NodeJS` shim inside `modules/local-vpn` or a sibling module and drive it over JNI + its message channel; the RN bridge was never the part we needed).
- **Hermes-loadable JS bundle — rejected.** Hermes runs no `node:` API at all; "the engine in Hermes" means a JS→native bridge per hot path — every socket, every TLS context, zlib inflate, h2 framing, the RSA keygen — i.e. reimplementing the engine's entire I/O in Kotlin while only the verdict layer stays JS. That layer effectively already exists (`matcher.ts` does DNS-grade verdicts in the RN bundle today). The entire value of P6 is running the SAME tested engine; a bridge pays port-grade cost for verdict-only parity.
- **Compiled-core/Kotlin port — rejected for P6, recorded as the exit strategy.** A from-scratch MITM core (TLS termination, h1/h2 relay, leaf forge, transforms, cosmetic injection, pin ledger) is a reimplementation with permanent double maintenance, not an embed. It stays on the table as the fallback if nodejs-mobile proves unbuildable/unsupportable — and crucially, everything outside the runtime choice survives a swap: the tun plumbing, the PROXY-v2 contract, the mode/fallback UX, and the CA-custody UX all live on the "accepts PROXY-v2 flows, returns bytes" side of the seam.

## Architecture (pinned)

```
app traffic ──► tun fd ──► readLoop
                              │ TCP dst:80/443 → TcpSession (UNCHANGED)
                              │    reassembled stream
                              ▼
                    LocalSocketUpstream (NEW — android.net.LocalSocket,
                    FILESYSTEM namespace, app-private dir)
                    write PROXY-v2 (src = app, dst = original packet dst)
                              │
                    engine data listener — unix socket <filesDir>/engine/proxy.sock
                    (nodejs-mobile thread inside VpnFilterService's process)
                              │
                    verdicts: SNI peek → tunnel | terminate | block
                    upstream TLS dials ride the app's UID — exempt because
                    the app is self-disallowed from its own tun (below)
                              │
              UDP/53 → existing DNS path (unchanged)
              UDP/443 → DROP (QUIC suppression, unchanged)
              other TCP/UDP → DirectUpstream + UdpDispatcher (unchanged)
```

- **Both engine listeners bind filesystem unix sockets** under `<filesDir>/engine/` (`proxy.sock` data, `control.sock` control) — never TCP loopback. Android's loopback is a shared bus: EVERY installed app can connect to `127.0.0.1:9294`/`:9293`, which on-device means an open forward-proxy AND the unauthenticated mutation surface (`/v1/proxy/toggle`, `/ca/rotate`, `/pins`) exposed to any app — the desktop's loopback trust model does not transfer. Filesystem sockets inside the app sandbox are unreachable to other UIDs at OS level; Node's `net`/`http`/`tls` listeners all bind unix paths through libuv, and `LocalSocket` connects to them from Kotlin. `LocalSocket` also needs no `protect()` — it isn't IP and can never enter the tun. The `sun_path` 108-char bound is a real constraint: the socket names stay short under `filesDir` (asserted at build).
- **Upstream egress exemption via self-disallowance** (pinned, with the escape recorded): the engine's upstream dials are ordinary sockets from the app's UID, and the broad capture routes would drag them straight back into the tun — the same recursion the desktop solves with the `_blockingmachine` service user. On Android the clean answer is `Builder.addDisallowedApplication(packageName)` while capture posture runs: the app exempts itself, so every socket its process makes — engine upstreams, hub dials, feed sync — bypasses the VPN by construction, and the hub-mode `protect()` calls simply become redundant-but-harmless. The honest cost is recorded: the app itself (its own WebViews, RN fetch) is unfiltered while capture runs — acceptable, it's the operator surface. The finer-grained alternative — passing `protect()`ed fds into libuv via `LocalSocket` ancillary fd-passing so the app stays filtered — is documented as the escape if self-exclusion proves wrong (Play policy, or a future want to filter the app's own traffic).
- **Engine lifecycle:** a `NodeEngineManager` (Kotlin) owns the nodejs-mobile thread inside `VpnFilterService`'s process — same-process for v1: the keystore channel and self-disallowance are per-UID anyway, and a `:engine` remote process buys OOM isolation at the price of re-solving IPC trust. Start/stop rides the capture arm/disarm; health = a channel heartbeat + data-socket accept probe; restart budget is bounded (3 crashes/60 s → failover ladder, no crash-loop under `START_STICKY`).
- **Failover ladder — never silent, always named:** engine unavailable (absent, failed start, crash-budget spent) → hub splice IF a hub is configured and the mode permits fallback → else fail-open (`DirectUpstream` claims :80/:443 too — web keeps working unfiltered, the DNS filter still applies; this mirrors the desktop's recorded fail-open posture). Every live posture surfaces in `httpsCaptureStatus` as `mode` (`engine`/`hub`/`passthrough`/`dns-only`) + `engineState` (`running`/`starting`/`down`/`absent`) — the card NAMES the active mode; a fallback never hides.
- **No DNS needed inside the engine:** PROXY-v2 hands the original-dst IP, so upstreams connect by address — the engine resolves nothing for spliced flows.
- **On-device bounds:** forge queue stays concurrency-1 (SNI-spray bound unchanged); `injectionBudget` drops to 16 (a phone doesn't hold ~32 MiB of eligible pages); leaf LRU stays 500; session cap 1024 + 256 KiB/flow upstream queue are the existing memory fences; Node's baseline RSS (~50-80 MB resident for the runtime + heap) is budgeted and measured at rehearsal, not hand-waved.
- **Foreground-service posture is already correct:** `VpnFilterService` runs `startForeground` with `FOREGROUND_SERVICE_TYPE_SPECIAL_USE`; the engine thread inherits it. Battery-optimization interplay (Doze, OEM killers) can still stall the process — that's one of the three named fallback triggers, not a surprise.

## Task 2 — engine Android port (`packages/https-filter` mobile entry + custody seams)

- `src/mobileMain.ts` — the spawnable entry paralleling `main.ts`: config from a JSON file path on argv (storeDir, rulesPath, socket paths, injectionBudget, `keyWrapBackend` mode), `startFilterProxy`-equivalent wiring, same graceful-shutdown contract on channel message / SIGTERM, same "one stderr line announces readiness" idiom so `NodeEngineManager` learns the engine is up.
- Unix-socket binds: extend `FilterProxyConfig`/`startProxy`/`startControlServer` to accept filesystem-socket paths (`dataUnixPath`/`controlUnixPath`, or `unix:`-prefixed bind hosts — implementation detail owned by the task, with `isLoopbackBindHost`'s refusal extended to accept the unix form since it's strictly stronger than loopback). The route table, origin guard, and `0xE0` TLV handling are reused unchanged — HTTP-over-unix keeps ONE implementation of `/v1/proxy/*`.
- `AndroidKeystoreBackend` (new `ca/` backend, injected — `resolveBackend` untouched): `load`/`store` round-trip the 32-byte wrap secret through the engine↔Kotlin channel to a `KeystoreSecretBox` that AES/GCM-seals it under an `AndroidKeyStore` key (no user-auth binding — the engine must unwrap while the VPN runs screen-off). Absent channel → `keyWrapBackend: null` → the honest 0600-plaintext fallback in app-private storage, `keyWrapped: false` on status, exactly the Linux-no-Secret-Service posture.
- `child_process` never ships on-device: the desktop keyWrap backends stay behind `resolveBackend`'s platform switch; the mobile entry injects its backend explicitly so `keyWrap.ts`'s spawn path is dead code in the bundle (asserted by T1's import-allowlist test).
- Mobile defaults: `injectionBudget: 16`, and `BM_PARENT_PID` has no meaning here — the manager IS the supervisor (channel heartbeat + restart budget), documented the way launchd's absence of `BM_PARENT_PID` is.
- Tests: `mobileMain` config-parse suite mirroring `main.test.ts`; channel-backend unit tests with a fake bridge; structural assertion that both listeners bind unix paths when configured; the existing unix-socket-naive tests stay green (desktop paths untouched).
- **Verify:** a jest leg (desktop-runnable) boots `mobileMain` against temp unix sockets + fake channel, splices a PROXY-v2 flow through `proxy.sock`, and gets a blocked-SNI refusal — the engine-side contract proven before any phone is involved.

## Task 3 — service wiring: `LocalSocketUpstream`, capture modes, failover ladder

- `tcp/LocalSocketUpstream.kt` — sibling of `QueuedSocketUpstream` (share the queue/worker machinery — refactor the common half rather than copy): `LocalSocket` connect to `proxy.sock` (FILESYSTEM namespace), `ProxyV2.encode(key, …)` preamble — byte-identical to `HubUpstream`'s, minus the `0xE0` TLV (the socket isn't network-reachable; in-band auth is meaningless inside the sandbox — recorded).
- `VpnFilterService`: `EXTRA_CAPTURE_MODE` (`engine`/`hub`/`off`) beside the sticky hub extras — hub mode is today's path untouched; engine mode arms `NodeEngineManager`, waits for readiness (bounded), then builds the capture `TcpDispatcher` with the `LocalSocketUpstream` factory. Broad routes + QUIC drop + UDP relay identical for both capture modes.
- Self-disallowance: `Builder.addDisallowedApplication(packageName)` whenever capture posture runs (engine or hub — the engine's upstreams need it; hub mode gains it for consistency with the recorded caveat that the app itself becomes unfiltered).
- Failover: engine-ready timeout/crash-budget → if `EXTRA_HUB_HOST` present and mode allows fallback → arm the hub `TcpDispatcher` and set `mode=hub`; else `DirectUpstream` claims :80/:443 (`mode=passthrough`) — DNS filtering unaffected. Engine returning to healthy does NOT silently re-arm mid-session; it re-arms on the next capture start (recorded, avoids flap).
- Status: `httpsCaptureStatus` gains `mode`, `engineState`, `fallbackReason` (nullable enum: `engine-absent`/`engine-crashed`/`engine-start-timeout`/`user-hub-mode`/`battery-killed`), flows counters unchanged. Notification text names the posture (`…filtering DNS + HTTPS on-device`/`via hub`/`passthrough — engine down`).
- `LocalVpnModule`/`localVpn.ts`: `startCapture(mode, hubHost?, hubToken?, hubPort?)` supersedes `startHttpsCapture` (kept as a deprecated alias delegating `mode='hub'` so nothing existing breaks), `captureStatus()` returns the extended map.
- Tests: JVM suite — mode-extra parse/stickiness, failover-ladder transitions (fake manager: down → hub → passthrough), `LocalSocketUpstream` queue/abort semantics against a real unix socket pair on the JVM (Linux CI can bind filesystem sockets — no Android needed for the transport test), PROXY-v2 preamble golden-vector parity with `HubUpstream`.
- **Verify:** unit-level proof that engine-down with no hub configured lands `passthrough` and names it in status; the adb rehearsal asserts the notification + status strings change when the engine is killed and restarted.

## Task 4 — CA custody on-device

- Store layout: `<filesDir>/https-filter/ca/` — `ca.pem`, `ca.key.enc` (keystore-wrapped via `KeystoreSecretBox`/`AndroidKeystoreBackend`) or `ca.key.pem` 0600 fallback; `policy.jsonl` beside it. `CertAuthority.open`/`forgeLeaf`/`rotate` run UNCHANGED — the 10-yr CA, 30-day leaf LRU-500 cache, `BMKEYWRAP1` envelope.
- `KeystoreSecretBox.kt`: AndroidKeyStore AES/GCM key (generated once, non-auth-bound, no `setIsStrongBoxBacked` requirement — software TEE-or-not is reported, not demanded) sealing the wrap secret to a file in the engine dir; the JS backend's channel calls are async so nothing blocks the Node loop.
- Device-CA install surface: the module exposes `deviceCaPem()` (reads `ca.pem` off the store dir — no engine socket needed) → JS computes the fingerprint with the existing `sha256.ts`/`fingerprintOfPem` → same confirm-dialog shape → same `installCaCertificate` KeyChain intent. New keys `bm.deviceEngine.caPem`/`caFingerprint` alongside the paired-hub-CA keys (which stay for hub mode); drift-detection reuse of `loadCaFingerprint`-style "changed since last confirmed" copy.
- The paired-hub CA and device CA are DIFFERENT trust roots — the card must never conflate them; each mode's CA section names which CA it installs ("this device's CA" vs "the hub's CA") and the cert name passed to KeyChain distinguishes them (`Blockingmachine Device CA` vs `Blockingmachine Hub CA`).
- Rotation: `POST /v1/proxy/ca/rotate` rides the unix control socket — reachable only from the app's own code, surfaced (if at all) behind the same explicit affordance the desktop card uses; pinned-out-of-scope for the card is fine, the API exists.
- Tests: `KeystoreSecretBox` JVM-shape unit tests with an injectable cipher provider (real Keystore needs instrumentation — honest mark), store-layout + migration tests on `CertAuthority` (desktop suite already covers; mobile adds only the channel-backend fixture), fingerprint-confirm flow tests reusing the hub-CA test seams.
- **Verify:** kill+reinstall rehearsal — uninstall wipes the store; a fresh install mints a NEW CA and the fingerprint line visibly differs (no cross-install CA reuse); `ca.key.enc` exists and `keyWrapped: true` on devices with a working keystore, `ca.key.pem` + `keyWrapped: false` honestly where there isn't.

## Task 5 — rules + policy on-device

- `syncRuleset` gains the fourth artifact: `GET <hub>:9191/browser.txt` → `ruleset_requests.txt` + `requestRuleCount` in `ruleset.meta.json` — the feed server already allows it; a hub that predates the artifact answers 404 → the engine simply starts on the DNS-derived request rules or empty (the engine's missing-ruleset posture is already "start empty, reload recovers"). DNS filtering keeps using `ruleset_native.txt` — the two artifacts serve different consumers and are NOT merged.
- Engine `rulesPath` → `ruleset_requests.txt`; after each sync the JS side pokes `POST /v1/proxy/reload` over the control unix socket (a fetch to `http://localhost/v1/proxy/reload` won't hit a unix socket — the module exposes `engineControl(path, method)` bridging to `LocalSocket`, or the reload rides the message channel; pick at implementation, the control route table is unchanged either way).
- Pin ledger stays device-local: `policy.jsonl` on the phone records pins learned on the phone; hub-mode pins live on the hub. They are deliberately NOT merged in v1 — recorded divergence, sync is a later feature if it earns one. `policyDegraded` ephemeral fallback already covers a corrupt store.
- `evaluateRequest`/`createCosmeticIndex` build cost on-device is measured, not assumed — `browser.txt` is the full artifact (P2 measured 129k cosmetic lines on the desktop baseline); if boot build is too slow on a mid-range phone the mitigation is a persisted compiled cache or a phone-trimmed artifact — flagged for T5 measurement, not pre-optimized.
- Tests: sync unit tests (artifact fetch, meta fields, 404-degradation), `toNativeRules` untouched, reload-bridge tests against a fake control channel.

- Tests: card-logic extraction into `src/filter/httpsCapture.ts` where the harness allows (mode persistence, status-render mapping incl. every `fallbackReason`, CA-source selection) — mirroring how the hub flow's logic already lives there for testability.

## Sequencing + non-goals

T1 (runtime embed — the gate everything waits on) → T2 (engine port) ∥ T3 seams once the unix-socket contract is pinned → T4 (CA) → T5 (rules) → T6 (UX) → T7 (docs/flags). Each lands separately reviewed. Non-goals: iOS anything (the entitlement wall stands; the `NEDNSProxyProvider` extension is the iOS story), a Hermes/bridge engine (rejected above), a Kotlin engine port (recorded escape only), per-app verdicts beyond flag 128's existing bypass, QUIC granularity (flag 122 stands), ECH beyond the spec's recorded passthrough, HTTP/3, explicit-proxy mode on the phone (splice covers transparent; CONNECT stays a desktop client surface), pin-ledger sync, and any change to the desktop engine's shipped postures.

## Risks

- **nodejs-mobile viability is the phase's existential risk** — sole maintainer, Node 18 (upstream-EOL), 16KB page-size merged-but-unreleased. Mitigations: pin a version + vendor the artifact, the T1 alignment gate, and the architecture's honest escape hatch (the runtime sits behind "accepts PROXY-v2, returns bytes" — a port can replace it without touching capture plumbing or UX).
- **APK bloat** — `libnode` is tens of MB per ABI compressed; AAB per-ABI delivery + a possible arm64-only first cut keeps it honest rather than ignored.
- **Battery/heat** — RSA-2048 forge per new SNI (~50-150 ms desktop, slower on-device) is serialized + deduped + LRU-cached, but a browsing session mints real keygen work; the injection budget, session caps, and the hub-fallback posture are the honest levers. Measured at rehearsal.
- **Memory** — Node baseline + buffers on a 4-8 GB phone under Android's per-app limits; the budgets are pinned (16 injection / 1024 sessions / 256 KiB-flow) but an LMK kill reads exactly like an engine crash — which is why the failover ladder + restart budget exist and why `engineState: down` is a first-class status.
- **Trust-model regression** — shipping a TCP-loopback engine on Android would hand every installed app an open proxy + mutation surface; the unix-socket pin prevents it — the risk is a shortcut during T2, mitigated by the structural test asserting no TCP bind in mobileMain.
- **Self-exclusion scope** — `addDisallowedApplication(packageName)` un-filters the whole app including its WebViews; recorded + flagged rather than discovered later.
- **Runtime parity** — same bundle on Node 18 (device) and ≥24 (desktop): behavior drift is possible at the margins (http2, zlib, tls details); the parity posture is "shared bundle + rehearsal-verified," honestly weaker than shared-runtime.
- **Play policy** — VPN + local MITM + user-CA install all need the declared-consent surface; the existing consent + KeyChain flows cover the mechanics, but a policy review line belongs to release prep, flagged rather than assumed clean.
- **Keystore variance** — StrongBox/TEE presence varies; the backend must degrade honestly (software-keystore wrap or the 0600 fallback) exactly like Linux's no-Secret-Service path.

## Open questions

- **AAR provenance** — npm-bundled artifact (inside `nodejs-mobile-react-native`) vs a Maven coordinate vs source build at a pinned tag; the vendor/ directory convention says "source with our patch," a binary AAR wants its own vendoring story — T1 decides and records.
- **Control-surface transport** — HTTP-over-unix-socket (route table reused wholesale) vs a channel-native JSON dispatcher (no HTTP server at all). Pinned default is HTTP-over-unix for implementation reuse; the channel alternative is there if unix-HTTP proves weird in nodejs-mobile's libuv.
- **`GET /v1/proxy/ca.pem` twin** — hub mode needed the data-port read-only CA surface because control stayed loopback; on-device the module can read `ca.pem` off the store dir directly, so probably no twin — confirmed at T4.
- **`browser.txt` size on-device** — full artifact verbatim vs a phone-trimmed compile output; measure evaluator build + RSS at T5 before deciding.
- **Process isolation** — same-process v1 is pinned; a `:engine` remote process is the recorded alternative if OOM isolation or lifecycle bugs demand it (costs: channel trust, keystore plumbing, PROXY-v2 fd reach — nothing impossible, all deferred).
- **Fallback re-arm** — engine recovery mid-session doesn't re-arm (recorded); if real-world flapping makes that annoying, hysteresis is a follow-up, not v1.

## Verification reality

Jest runs the whole engine-port leg (unix-socket listeners, channel backend, mobileMain config, failover-ladder logic, card logic) on this Mac and CI — no phone required for the contract tests. JVM unit tests cover the Kotlin seams the same way P4's TCP core did. The parts only hardware/emulator can prove — VpnService grant, tun capture, engine-in-service lifecycle, battery/Doze behavior, KeyChain install, the airplane-mode flag-125 verify — are operator-gated behind `scripts/android-engine-rehearse.sh` and named here rather than pretended green. CI gets the structural assertions (bundle import allowlist, unix-bind-only in mobileMain, 16KB alignment check where tooling exists) so the risky parts can't silently regress.
