# Known Issues

Flagged but unfixed work, and the decisions behind it, recorded the moment it is flagged rather than left in conversation. An entry states why it was left, what it would take, and how a fix could be verified. Closed entries move to `closed-issues.md` with the commit that closed them, so the list doubles as a record of what was deferred and when it was picked up.

Nothing here is scheduled. The list exists so nothing is *relied on* silently.

Open entries are grouped by the kind of attention they need — an owner decision, work only a person can do, or nothing human at all.

- **Why left:** the third mechanism — `update-ca-trust`/`trust anchor` on RHEL/Fedora-likes and anything further afield — is a second system-store write path that needs its own verification pass; probing the RHEL bundle for *presence* is free, but writing it honestly is not the same op as the Debian flow.
- **Decision (2026-10-27):** do it — add the `update-ca-trust` anchors write path as a third needs-admin escalation.
- **Fix shape:** add the `update-ca-trust` anchors path (`/etc/pki/ca-trust/source/anchors/` + `update-ca-trust extract`) as a third needs-admin escalation with its own rendered command line.
- **Verify:** `caTrustStore.test.ts` forces `linuxSystemStore` probe paths to empty + a rejecting runner to hit the 'unsupported' leg today; closing this means a RHEL-family box (or a mocked probe) where install returns `needs-admin` with an `update-ca-trust` line instead.

### 118. The linux capture installer is systemd-only — sysvinit/openrc/alpine die honestly (`sysvinit-openrc-capture`)

- **Where:** `scripts/install-linux-capture.sh` (the `systemctl` gate that dies naming the unsupported inits), the linux branch of `isCaptureServiceInstalled` in `packages/electron-app/src/filterProxyManager.ts` (probes `/etc/systemd/system/blockingmachine-proxy.service` only).
- **What:** the linux capture install is a systemd unit + an iptables `REDIRECT` anchor supervised by `Restart=always`; on a sysvinit/openrc/alpine host the installer refuses with a named-unsupported error rather than half-installing, and the manager's installed-probe cannot see a non-systemd service anyway.
- **Why left:** the supervision contract is the load-bearing piece — capture owns the redirect anchor, so helper death must be fail-closed-until-restarted (systemd gives that); openrc/sysvinit restart semantics differ and writing them blind would claim a posture the code cannot prove.
- **Decision (2026-10-27):** do it — openrc + sysvinit supervisor wrappers around the same `bm-anchor.sh` core, with the matching installed-probe branches.
- **Fix shape:** an openrc service file + a sysvinit init script that replicate the redirect anchor and restart-on-death semantics, plus the matching probe branches — same `bm-anchor.sh` core, new supervisor wrappers.
- **Verify:** an openrc or sysvinit box where the install script completes, `isCaptureServiceInstalled` reports true through the new probe, and killing the helper shows the supervisor restart keeping the anchor fail-closed.

### 120. WinDivert stays the documented Windows fallback — named, never silently substituted (`windivert-fallback`)

- **Where:** `docs/https-filtering-p3-plan.md` (the fallback note), the `BM_WFP_PATH_STATUS` banner in `helper/windows/redirect-helper.c`.
- **What:** the design spec's original Windows mechanism was a WinDivert driver + userspace NAT in both directions; P3 superseded it with the driverless WFP connect-redirect + the system-provided callout. The recorded rule: if the records/context API proves environment-fragile on real Windows, the escape is the spec's WinDivert design — implemented deliberately as its own task, never swapped in mid-failure.
- **Why left:** WinDivert means a third-party kernel driver to vendor and sign plus a userspace NAT doing both directions — strictly more machinery than the session-dynamic WFP path, which already gives the fail-open posture the architecture wants. The flag exists so the fallback stays a decision, not a drift.
- **Fix shape:** only if flag 119's rehearsal shows the WFP path unusable — a new helper TU driving `WinDivertOpen`, a driver ship/sign plan (a release-pipeline question of its own, flag 124), and the same PROXY-v2/splice contract downstream.
- **Verify:** the structural suite asserts the helper never links `windivert.h`/`WinDivertOpen`; the flag closes when the WFP path validates (fallback moot) or a planned WinDivert adapter ships deliberately.

### 121. Linux capture is REDIRECT + SO_ORIGINAL_DST — TPROXY was evaluated and deliberately not chosen (`tproxy-not-chosen`)

- **Where:** `helper/linux/redirect-helper.c` header, `helper/linux/bm-anchor.sh` rule renders, the plan's platform-decision line.
- **What:** REDIRECT rewrites the flow's destination to loopback and conntrack remembers the original — recovered with a plain `getsockopt(SO_ORIGINAL_DST)`/`IP6T_SO_ORIGINAL_DST`, no socket flags, no policy routing. TPROXY would need ip-rule/ip-route plumbing plus `CAP_NET_ADMIN` on the socket itself — strictly more moving parts for zero gain: the helper needs the original destination, not full transparent-proxy address preservation through the upstream side.
- **Why left:** recorded decision, not a gap — the nft/iptables REDIRECT path was live-rehearsed in a NET_ADMIN container (`scripts/linux-capture-rehearse.sh`) and the structural suite pins the absence of the TPROXY sockopts.
- **Fix shape:** none planned; revisit only if semantics beyond origdst are ever required (e.g. preserving the client source on the upstream side — out of scope for a loopback capture).
- **Verify:** `helper-linux.test.ts` asserts no `IP_TRANSPARENT`/`IP_RECVORIGDSTADDR`/`SOL_TRANSPARENT` in the helper; the docker rehearsal is the standing proof.

### 122. QUIC suppression drops ALL of UDP/443 — the per-user scoping question stays open (`quic-udp443-granularity`)

- **Where:** `helper/linux/bm-anchor.sh` renders (`udp dport 443 drop` / `-t filter … -j DROP` after the skuid RETURN), the macOS pf anchor's `block drop … user != _blockingmachine` line.
- **What:** UDP/443 is invisible to a TCP capture, so it is dropped to force the HTTP/3→TCP fallback the redirect can see. The drop is scoped like the capture itself — OUTPUT-hook only (locally-originated flows; forwarded traffic never traverses it) and behind the service-user exemption so the engine's own QUIC dials survive — but every other local process loses QUIC too, not just browsers under capture.
- **Why left:** accepted granularity — no netfilter primitive scopes a drop finer than skuid, and the HTTP/3 fallback is the designed behavior (clients retry TCP/443). The trade is recorded: a non-browser UDP/443 application on the same host is collateral.
- **Decision (2026-10-27):** make it configurable — a per-user QUIC opt-out (extra exempted uids/users rendered as additional RETURN rules ahead of the drop) so a host running a real QUIC workload can spare it without giving up suppression for everything else.
- **Fix shape:** if a real workload surfaces, scope finer — e.g. exempt additional named uids via a second RETURN, or drop only for dports that would otherwise be captured; nothing narrower exists today.
- **Verify:** the rendered rules carry the exemption-first ordering; the docker rehearsal's allow leg proves the fallback works end-to-end.

### 125. Android HTTPS capture depends on a LAN hub — an on-device engine (nodejs-mobile) is the full-MITM-without-hub track (`android-no-ondevice-engine`)

- **Where:** `packages/mobile/modules/local-vpn` (`VpnFilterService` + `tcp/` — the thin adapter), `docs/https-filtering-p4-plan.md` non-goals.
- **What:** P4's shipped posture is hub-dependent by design: the phone reassembles TCP :80/:443 out of the tun fd and splices each flow to `<hub>:9294` (PROXY-v2) — every verdict lives in the desktop engine, so filtering stops the moment the phone leaves the hub's network. A real on-device engine (nodejs-mobile or equivalent running the same `https-filter` core inside the app) would give full MITM off-LAN — its own CA, forge, evaluator — with no hub at all.
- **Why left:** an on-device engine is a phase of its own — JS runtime packaging inside an Android service, per-flow CA key custody on the handset, battery/lifecycle pressure the hub posture sidesteps entirely. P4 deliberately ships the thin adapter first (the plan's "byte-dumb phone" architecture); the hub dependency is the recorded posture, not an oversight.
- **Decision (2026-10-27):** both — the on-device engine becomes the default posture and the LAN hub the fallback (the phone runs its own MITM when it can, and splices to the hub when the embedded engine is unavailable or unwarranted).
- **Plan written (2026-10-27):** docs/https-filtering-p6-plan.md — on-device engine default + hub fallback per the decision; flag stays open until the first task lands.
- **Fix shape:** embed the engine package under a mobile JS runtime, reuse `VpnFilterService`'s tun plumbing with a loopback listener instead of the hub socket, and re-point the CA surfaces at the on-device store. Sizeable enough to deserve its own plan document.
- **Verify:** capture runs with no hub reachable — a blocked SNI is refused on-device with the phone off the LAN.

### 126. Apps targeting API 24+ ignore user CAs — hub MITM covers browsers and opted-in apps only (`android-cert-trust-ceiling`)

- **Where:** `docs/https-filtering-design.md` §2 (the platform table) + §10; `packages/mobile/app/(tabs)/settings.tsx` HttpsCaptureCard copy.
- **What:** installing the hub CA into the device's user store does not make arbitrary apps trust it — since API 24 an app must opt into user CAs via `networkSecurityConfig`, so full-MITM content filtering on Android reaches browsers and opted-in apps only. SNI-level verdicts (peek → block/tunnel) cover every app regardless, which is why the shipped card says "hostname blocking for every app, content filtering where the CA is trusted".
- **Why left:** a platform ceiling, not an engineering gap — unfixable without per-app packaging tricks the product does not do. Documented in the design and the card copy rather than promised.
- **Fix shape:** none for the ceiling itself; keep every surface wording honest (the mobile card, this entry, and the design already agree). If a future per-app opt-in story ever exists (device-owner/enterprise profiles), it lands as its own feature.
- **Verify:** the honest-statement check — an opted-out app tunnels at SNI level (hostname verdict applies, content is never inspected) while a browser on the same device is fully filtered.
